# 要求は、実装の前に「実際に起きたか」「動かして確かめたか」を根拠として確かめる

## TL;DR

- 要求を細かく固めても、根拠の弱い判断は止まらなかった。Issue ごとに、その要求が要ることの根拠を、種類と所在のそろった行で書かせることにした。実際には起きていない要求は、そう示したうえで、合意する人が決める。
- feedback-loop の mutation では、既存の道具を文章で退けた 1 つの判断の上に、19 件の PR と約 12,000 行が積まれていた。退けた理由 3 つのうち 2 つは、道具を動かすと成り立たなかった。
- Bug の Issue の出どころを 4 つの repo で読み分けた。利用で動いている部分は、Bug の大半が実行から来ていた（dotclaude は 13 件中 9 件）。利用から Bug が上がらない部分は、見直しから来ていた（recall は 24 件中 15 件、利用からは 0 件）。
- 決定の記録（DR）も、前提が崩れたときに見直せる形になっていなかった。見直す条件が閉じた一覧で、退けた案の理由が変わる場合を含んでいなかった。
- この決まり自体も、1 日で 5 回広げた後に、独立した評価を 2 回受けて、3 つの種類と 1 文に縮んだ。決まりを作る側でも、確かめる前に積む形が起きた。
- 分類は 1 人が 1 日で本文を読んだ結果である。見直しで見つけた修正が、後の事故を防いでいたかは確かめていない。決まりは Issue にした段階で、効果は測っていない。検証日は 2026-11-23、モデルは `claude-fable-5-2`。

## 結論

Issue にする要求は、種別や大きさによらず、その要求が要ることの根拠を持つ。根拠は、種類と所在を決まった形で書く。見直しで見つけ、実際には起きていない要求は、「実際には起きていない」と示したうえで、合意する人が決める。

thkt はこれを証明に置き換えて決めた。根拠の無い 1 歩が混ざると、その上に積んだものが全部疑わしくなる。

| 証明 | コードベース |
| --- | --- |
| 公理 | repo の `OUTCOME.md` と、日付つきの持ち主の決定 |
| 補題 | 合意した Issue |
| 仮定つきの補題 | DR。前提が成り立つ間だけ使える |
| 推論の 1 歩 | 1 つの変更。どの公理か補題から導いたかを指す |
| 予想 | 見直しで見つけ、実際には起きていない穴。記録はするが、その上に積まない |

根拠の種類は 3 つである。見直しで見つけた穴にも、落ちるテストは必ず書ける。テストと、動かした出力は「欠陥がある」を示すが、「直す必要がある」は示さない。そのため、この 2 つは種類に入れず、主張の裏付けとして扱う。

| 種類 | 当たるもの | 当たらないもの |
| --- | --- | --- |
| 観測 | 利用か実行の中で、確かめようとせずに起きたこと。人からの報告と、上流の告知を含む | agent が、確かめるために動かした結果。再現、試しのコード、見直しをした agent の指摘 |
| 決定 | 合意する人が、自分からその要求を述べた発言。または、agent が持ち込んだ要求について、「実際には起きていない」を示した問いへの回答 | その 1 文を示していない問いへの回答。「進めて」のように、中身を述べていない返事 |
| 上位の要求 | 合意済みの Issue が、その作業を範囲に名指ししていること | repo の `OUTCOME.md` と DR。どの変更も結び付けられるので、必要の根拠にはしない |

この決まりのもとでも、どの要求も 1 往復で通る。合意する人が「それでも要る」と答えれば、Issue になる。決まりが足すのは、その 1 往復に「実際には起きていない」の 1 文を必ず出すことと、何を根拠に Issue にしたかを本文に残すことである。

この仕組みが確かめるのは、要求が根拠の形に従っているかである。要求の意図が正しいかは確かめない。意図の正しさは、合意する人が根拠の行を読むところに残る（[formal-verification-intent-poteto.md](../sources/formal-verification-intent-poteto.md)）。

## 採用した理由

| 分かったこと | 根拠 |
| --- | --- |
| 要求の細かさは足りていた。足りなかったのは、要求の出どころである | feedback-loop の mutation の Issue は、受け入れ条件、前提、範囲外まで書かれていた。それでも、2026-11-18 以降の mutation の PR 19 件（機能 9 件、バグ修正 10 件）の後に、独自の実装を既存の道具へ置き換える判断になった（[thkt/feedback-loop#251](https://github.com/thkt/feedback-loop/issues/251)） |
| 文章で書いた「足りない理由」は、動かすと崩れる | [DR-0001](https://github.com/thkt/feedback-loop/blob/9b36bfa/docs/decisions/0001-mutation-generation-and-application.md) は、mizchi/mutator を退ける理由を 3 つ書いた。「Bun テストに対応しない」は、DR が accepted になった 2026-11-19 に、mutator が Bun の runner を含む 0.5.0 を出して古くなった。「Node.js 24 以上を要する」は、`node` を PATH から外しても最後まで走った。「子プロセスに届かない」は今も成り立つが、約 85 行の preload を足すと届いた |
| 判断の基準が、対象でないものを根拠にしていた | DR-0001 は「子プロセスで動くコードにも届く」を基準に置いた。根拠はその repo 自身のテストの形で、対象である導入先では確かめていなかった |
| 使われていない部分の Bug は、見直しからしか来ない | mutation は、Issue の本文が「まだどの版にも入っていない」と書く状態で、Bug 9 件のうち実行だけで起きたものは 1 件だった。同じ repo の mutation 以外は、複数の導入先で動いていて、Bug 15 件のうち 10 件が実行から来ていた |
| 見直しで見つけた穴は、別の repo でも同じものが見つかる | 「別のプロセスグループの孫が pipe を開いたままにする」場合を、2 つの repo が別々に直していた。どちらも見直しが出どころで、片方の Issue は「実際の観測はない」と書いていた |
| DR の狙いが、要求の出どころになる | feedback-loop の 2 件の Bug は、「DR-0002 の狙いと合わない」「DR-0002 が防ぐ状態である」を理由にしていた。どちらも、実際の利用では起きていなかった |
| DR の見直す条件は、閉じた一覧として読まれる | DR-0001 の条件は 2 行で、どちらも選んだ案を広げる条件だった。手元の rules は「既存構造の削除や統合を提案する前に、関連 DR の見直す条件を読み、未達かどうかを判定する」と定める。このとおりに読むと、置き換えを提案しない結論になる |
| 退けた理由を書いた DR は、覆す手がかりになる | DR-0001 が理由を行として書いていたので、何を動かせば確かめられるかが分かった。DR を無くすのではなく、理由と前提を確かめられる形で書く |

## 却下した案

| 案 | 却下した理由 |
| --- | --- |
| 要求をより細かく固める | 細かさは既に足りていた。要求を固める工程は、入ってきたものを精密な Issue にする。入ってくるものが見直しの指摘だと、精密な Issue が実装され、それがまた見直される。この輪に、利用からの信号が入る場所が無い |
| 根拠を求める対象を、独自の実装や DR などの大きい変更に絞る | 担当の agent が出した案で、thkt が退けた。小さい 1 歩でも、根拠が無ければ、その上が疑わしくなる。絞るのは対象ではなく、根拠の大きさにした。数行の修正の根拠は、直す前に落ちるテスト 1 つで足りる |
| Bug の出どころを、本文の語で数える | 試して、読んだ結果と合わなかった。feedback-loop の Bug 27 件では、語の一致は「実行」12 件、「両方」14 件、「見直し」1 件と答えた。Issue の雛形の見出し「Steps to Reproduce」が、実行を表す語に当たっていた。本文を読むと、mutation の 9 件だけで見直しが 5 件あった |
| 根拠の種類を 5 つか 6 つにする | 最初の案は、落ちるテスト、実行の出力、先行実装も種類に入れた。評価で、先行実装は、探すのも判断するのも agent で、人を通らずに通す道だと指摘された。同じ手当てを持つ実装があるなら、まずその実装を採る話である |
| 根拠を示せない要求は、Issue にせずに止める | 働かない。要求を固める skill は、止まらずに人に問う。人が「要る」と答えれば、それが決定になる。主張を「知ったうえで決めた要求だけを Issue にする」に下げた |
| 見直しで見つけた Bug に「着手の条件」を書いて、Issue として残す | 書いても働かない。実装する側の skill を変えないので、止めるものが無い |
| コードの後方互換を残さない決まりを、全ての repo の rules に入れる | 止めた。評価で、本番の DB の migration を文字どおり禁じること、plugin の利用者の設定ファイルを壊すこと、データを守る行が働かないことを指摘された |
| 本文の根拠の行を検査する script を、先に作る | 作らなかった。agent が行を落とすか、所在を作文するかは、まだ観測していない。週ごとの集計で未記入の件数を見て、落とすと分かってから足す |
| DR をやめ、コードだけを正とする | コードは「何をしているか」を持つが、「なぜ別の案を採らなかったか」を持てない。DR-0001 を覆せたのは、退けた理由が書かれていたからである |

## 検証

| 項目 | 内容 |
| --- | --- |
| 検証日 | 2026-11-23 |
| モデル | `claude-fable-5-2` |
| ツール | GitHub CLI（`gh`）、Bun 1.4.5、`@mizchi/mutator` 0.5.0 と 0.5.3 |
| 対象 | thkt の 4 つの repo の、2026-10-24 以降に作られた Bug の Issue。feedback-loop は main `9b36bfa`、mutator は main `07e0413` |

### 再現手順

1. Issue を取得する：`gh issue list -R thkt/<repo> --state all --limit 1000 --search 'created:>=2026-10-24' --json number,title,labels,body,createdAt,state`
2. Bug を選ぶ：title が `[Bug]` で始まるか、`bug` のラベルを持つ Issue を残す。
3. 本文を読み、出どころを 1 つ決める：利用や実行で起きた、見直しや棚卸しで見つけた、テストの不安定（コードを変えずに落ち、走らせ直すと通る）、本文から決められない、のどれかにする。
4. 試しの Bun プロジェクトを作る：`src/` に 3 ファイル、`bun:test` のテストを 2 ファイル置く。1 つのテストは実装を import して呼び、もう 1 つは `Bun.spawnSync(['bun', 'src/cli.ts', …])` で実装を起こす。
5. mutator を入れる：`bun add -d @mizchi/mutator@0.5.3`。設定は `runner: 'bun'` にする。
6. `node` を PATH から外して走らせる：`bun node_modules/.bin/mutator`
7. 子プロセスへ届かせる preload を足して走らせる：`BUN_OPTIONS="--preload=<preload>" bun node_modules/.bin/mutator`。preload のコードは [thkt/feedback-loop#251 のコメント](https://github.com/thkt/feedback-loop/issues/251#issuecomment-7093643440)にある。

### 結果

Bug の出どころは次のとおりだった。

| repo | Bug | 利用や実行で起きた | 見直し・棚卸しで見つけた | テストの不安定 | 本文から決められない |
| --- | --- | --- | --- | --- | --- |
| recall | 24 | 0 | 15 | 0 | 9 |
| cantle | 21 | 2 | 6 | 11 | 2 |
| dotclaude | 13 | 9（うち 2 はテストの不安定） | 1 | | 3 |
| feedback-loop の mutation 以外 | 15 | 10 | 2 | | 3 |
| feedback-loop の mutation | 9 | 1（ほかに、見直しと実行の両方が 3） | 5 | | |

- recall の 24 件は、16 件が優先度 low で、再現はどれも合成した入力だった。
- cantle の 11 件は、どれも「負荷の高いときにテストが時間切れになる」で、原因は 1 つだった。テストごとに 1 件ずつ直していた。
- feedback-loop の `src/` は 5,657 行で、mutation の 5 ファイルが 1,798 行だった。

mutator の試しは次のとおりだった。

| 走らせ方 | 実行した壊し方 | 検出 | 実行されなかった（`NoCoverage`） |
| --- | --- | --- | --- |
| mutator だけ | 20 件中 9 件 | 9 件 | 6 件 |
| preload を足す | 20 件中 16 件 | 16 件 | 0 件 |

`node` が PATH に無い状態で、どちらも終了 0 で終わった。mutator の README は、本体を Node.js で動かすと書いていて、Bun での実行は作者が保証していない。

### 導入先での測定

mutation の置き換えは、別の session が導入先 2 つで測った（[thkt/feedback-loop#251](https://github.com/thkt/feedback-loop/issues/251) に記録）。この頁の筆者は、結果を読んだだけで、自分では走らせていない。

| 見た点 | 結果 |
| --- | --- |
| 今の実装だけが拾えた検出 | 0 件。同じモジュール（83 件）で、今の実装だけが検出とした 14 件は、11 件が型検査に通らない壊し方、3 件が負荷で落ちるテストによる偶然だった |
| 1 件あたりの時間 | 今の実装は約 45 秒、mutator は約 1.5 秒 |
| preload を足した mutator が判定できない壊し方 | cantle で 7,649 件中 57 件、dotagents で 15,900 件中 25 件 |
| 追加で要ったもの | TypeScript 7 の導入先では、mutator の型検査が Bun の上で落ちる。壊す前のテストが、負荷で落ちることがある |

thkt は、この結果を見て、置き換えると決めた。

### 決まりを作る側で起きたこと

要求に根拠を求める決まりを、この頁の筆者（agent）が Issue にした。その過程で、feedback-loop で見たのと同じ形が起きた。

| 段 | 起きたこと |
| --- | --- |
| 1 日で 5 回広げた | Bug の出どころを書かせる案から始め、全ての種別、DR の扱い、合意の示し方、先行実装と足した。どれも、実装も評価もしないまま足した |
| 1 回目の評価 | 独立した評価（critic-design）を、3 つの Issue に通した。必須の指摘は、合わせて 20 を超えた。根拠の種類は、どれも agent が自分で埋められた。rules と skill が plugin として配られ、仕事の repo にも読み込まれることを、見ていなかった |
| 筆者の事実の誤り | DR の件数を 131 件と書いた（`README.md` を数えていて、実際は 130 件）。「後方互換の方針は、指示のどこにも無い」と書いた（検索の当たりを、無関係と見て落としていた）。自分で定めた「観測」に、自分の見直しの作業を書いた |
| 2 回目の評価 | 芯だけに書き直した版にも、必須の指摘が 3 つ出た。「根拠が無ければ止まる」は働かないこと、節の置き場所が今あるテストを落とすこと、完了条件が実装の途中の作業になっていること |
| 残ったもの | 3 つの種類と、「実際には起きていない」の 1 文 |

効いたのは、形式を足すことではなく、別の目で読み直すことだった。thkt が 4 つの問いに 4 つとも先頭の選択肢を選んだときも、偏りに気づいたのは、後から別の session が読み直したからである。

### 確かめていないこと

- 見直しで見つけた修正が、後で実際の事故を防いでいたか。
- Feature の Issue の出どころ。読んだのは Bug だけである。
- 根拠の行を書かせた後に、見直しが出どころの Bug が減るか。#959 と #960 は、まだ実装していない。#959 の最後の版は、3 回目の評価を受けていない。
- 「実際には起きていない」の 1 文で、合意する人の答えが変わるか。問いの先頭の選択肢を選ぶ癖には、手当てをしていない。
- Vitest の導入先での動作。mutator の Vitest の runner は、Node.js では走ったが、Bun だけでは Vitest 自体が走らなかった。手元に、Vitest 5 の導入先は無い。
- 130 件ある dotclaude の DR のうち、前提が古くなったものが何件あるか。

## 見直す条件

- 週ごとの集計が 4 週分たまったとき。見直しが出どころの Bug の割合が変わったかを見る。
- 見直しで見つけ、Issue にしなかった要求が、後で実際に起きたとき。決まりの費用として記録する。
- #959 が入った後に、根拠の行の無い Issue か、実在しない所在が続いたとき。本文を検査する script を足すかを決める。
- feedback-loop#251 の測定で、mutator と preload では足りないと分かったとき。「動かせば足りると分かる」という今回の観察を、書き直す。
