# agent は、コメントを消したコードでも、テストの無い規則を消さなかった

## 結論

**コメントを消しても、agent が規則を消す回数は増えなかった。** 「過剰な防御と不要なコードを取り除く」作業を18回させ、テストの無い規則12種は18回すべてで残った。コメントあり、コメントなし、コメントなしでテストあり、の3条件で差は無かった。

この結果を受けて、feedback-loop が導入する検査の候補に、コメントの検査を加える Issue を起こした（[thkt/feedback-loop#186](https://github.com/thkt/feedback-loop/issues/186)）。検査の形は次の表のとおりである。計測が確かめたのは、コードから理由を読み取れる規則だけで、コードから読み取れない外の事実は確かめていない。

| 項目 | 決めた内容 |
| --- | --- |
| 対象 | 変更したファイルにあるコメント。変更の前からあるコメントも含む |
| 弱（既定） | TODO、FIXME、HACK、workaround、暫定などの語を持つコメントが失敗する。Issue 番号を持てば通る |
| 中 | 弱に加えて、`//` の行コメントが失敗する。JSDoc と、参照（URL、Issue 番号、DR 番号）を持つコメントは通る |
| 強 | コメントがすべて失敗する。参照を持つコメントは通る |
| 導入 | 一律には入れず、導入先ごとに必要性を判断する |

実現方法は決めていない。

## AI の読み手から見た3つの観点

人が読むコードでは、コードに持たせられない why と why-not をコメントに残す。読み手が agent になると、次の3点で前提が変わる。

| 観点 | 中身 | 根拠の状態 |
| --- | --- | --- |
| AI は文章を強く信じる | 人は古いコメントを読み飛ばす。agent は、コードと食い違うコメントに従うことがある | 推論。手元で測っていない |
| AI はコメントを写し、増やす | 既存のコメントが多いほど、新しいコードにも同じ調子のコメントが付く。応急処置を正当化するコメントも、既存のパターンとして写される | [all-code-is-slop-poteto-talk.md](../sources/all-code-is-slop-poteto-talk.md) の講演が、タイマーの広がりを1件挙げる。今回の作業はコードを削るもので、新しいコメントはどの条件でも0行だった。測れていない |
| AI には読む前の注意書きが要りにくい | 規則を破れば検査が落ち、agent は診断を読んで直す。人と違い、やり直しの費用が小さい | 一部を測った。agent はコメントが無くても規則を残した。ただし、検査が落ちて直す経路は一度も起きず、agent はコードを読んで理由を導いた |

3つ目の観点は、条件を1つ含む。規則を持つ検査が無い repo でコメントを消すと、規則を述べた文章はどこにも残らない。

## コメントの行き先

コメントの中身は、3つに分けられる。

| コメントの中身 | 行き先 |
| --- | --- |
| 破ると振る舞いが変わる制約 | テストの名前か、lint の文面 |
| 判断の理由と、却下した案 | DR か commit message |
| テストにできない理由。並行性の説明や、手元で確かめられない外の事実など | コメントに残る |

コメントを禁止しても、文章は無くならない。lint の文面もテストの名前も文章である。変わるのは置き場所で、コメントは常に見えて強制されず、検査の文面は破ったときだけ見えて、現実とずれると検査が落ちる。

## 採用した理由

- **コメントを消す損が、観測されなかった。** コメントだけが規則を述べていた2箇所（`E01`、`P01`）は、コメントを消した12回すべてで残った。
- **コメントが持つ規則は少なかった。** テストに拾われなかった12種のうち、コメントが規則を述べていたのは2種で、9種にはコメントもテストも無かった。コメントとテストが同じ規則を持つ箇所は5つあった。
- **既定の弱は、今あるコードをほとんど落とさない。** feedback-loop の `src/` のコメント297行で、弱が対象にする語を持つ行は0行だった。語で自己申告しない正当化は、弱では通る。
- **コメントもテストも無い規則は、誤っていても気づけない。** `B01` が壊した規則は、後でバグとして直された。この種類は、コメントの検査では見つからず、壊した実装で測って見つかった。

## 却下した案

| 案 | 却下した理由 |
| --- | --- |
| 強さを1つに固定し、参照を持つコメントだけを通す | 実際の運用には厳しすぎると判断した。強さを3段階にし、既定を弱にした |
| 変更で足した行のコメントだけを対象にする | 触ったファイルなら、前からあるコメントも対象にしてよいと判断した |
| why と why-not のコメントは残す、という今の基準を変えない | 講演の失敗例は「応急処置が許される理由」を書いたコメントで、形式上は why にあたり、この基準を通る |
| 変更していないファイルのコメントも一度に対象にする | 外の事実を述べるコメントを消したときの影響を、測っていない。触ったファイルから進める |

### 再現手順

照合は、次の手順で行う。

1. [measure-tests-before-adding-practices.md](measure-tests-before-adding-practices.md) の手順で、壊した実装45種と、拾われなかった12種を固定するテスト14件（`tests/classification-gaps.test.ts`）を用意する。
2. 拾われなかった12種について、壊した行を `diff` で特定する。
3. `src/classification.ts` のコメント13行について、各コメントが説明するコードの行を読み、12種の壊した行と突き合わせる。
4. `git log 4cc7995..HEAD -- src/classification.ts` で、その後の変更を読む。

agent での計測は、次の手順で行う。

5. 条件ごとに repo を `git clone` し、`node_modules` へ symlink を張り、次の表の状態を作って commit する。

| 条件 | `src/classification.ts` のコメント | 12種を固定するテスト |
| --- | --- | --- |
| A | あり（13行） | 置かない |
| B | 消す。`grep -v -E '^[[:space:]]*//'` を通す | 置かない |
| C | 消す | `tests/classification-gaps.test.ts` を置く |

6. 各条件の repo に `verify.sh` を置く。中身は `bun scripts/build.ts && bun test --timeout 60000 ./tests/config.test.ts ./tests/standalone.test.ts ./tests/batch.test.ts ./tests/results.test.ts ./tests/cli.test.ts ./tests/entrypoints.test.ts` で、条件 C では末尾に `./tests/classification-gaps.test.ts` を足す。
7. 3条件とも、変更の無い状態で関係する6ファイルの189件と、14件のテストが通ることを確かめる。
8. 条件ごとの repo をさらに `git clone` し、agent を実行する。`claude -p --model <sonnet|haiku> --permission-mode acceptEdits --allowedTools "Bash(bash verify.sh),Bash(bun:*),Bash(git status:*),Bash(git diff:*),Bash(git log:*)" --output-format stream-json --verbose "<prompt>" < /dev/null`。2つのモデルで、条件ごとに3回、計18回である。
9. agent の結果を別の場所へ複製し、14件のテストを置き、`bun scripts/build.ts` の後で14件と関係する6ファイルを実行する。落ちたテストの名前を読む。
10. `git diff HEAD -- src/classification.ts` と、出力の `result` を読む。

手順8の prompt は次のとおりである。

```text
src/classification.ts から、過剰な防御と不要なコードを取り除いてください。

- 利用者から見える振る舞い（終了コード、診断の文面、分類の結果）は変えないでください。
- 手で編集するのは src/classification.ts だけです。テストは変更しないでください。
- 終わったら `bash verify.sh` を実行し、通ることを確かめてください。verify.sh は生成物を作り直してから、関係するテストを実行します。
- 最後に、取り除いたものと、検討して残したものを、理由を添えて一覧にしてください。
```

### 結果

照合の結果は次のとおりである。テストに拾われなかった12種のうち、コメントが規則を述べていたのは2種だった。

| 壊した箇所の状態 | 種 | 数 |
| --- | --- | --- |
| コメントが規則を述べ、テストは無い | `E01`、`P01` | 2 |
| コメントはあるが、境界値までは述べていない | `O02` | 1 |
| コメントもテストも無い | `A04`、`A05`、`B01`、`C01`、`F01`、`F04`、`R03`、`R04`、`R08` | 9 |

- コメントとテストの両方が同じ規則を持つ箇所は5つあった。`E02`、`O01`、`O03`、`P02`、`R06` が壊した行である。
- `B01` が壊した規則は、コメントもテストも無く、後でバグとして直された。commit `79f29ba`（2026-11-15）は、名前が `.` で始まるテストファイルを一覧から外す条件を取り除き、テスト27行と、Bun の挙動を述べるコメント1行を足した。
- 先の計測で agent が書いたテストの1件は、`B01` の直される前の挙動を固定していた。

agent での計測の結果は次のとおりである。18回すべてで、14件のテストと関係する189件が通った。

| 条件 | 消えた規則（sonnet 3回） | 消えた規則（haiku 3回） | `entryExists` を書き換えた回 |
| --- | --- | --- | --- |
| A：コメントあり | 0 | 0 | haiku の1回 |
| B：コメントなし | 0 | 0 | sonnet の1回 |
| C：コメントなし、テストあり | 0 | 0 | haiku の1回 |

- **agent は、コメントが無くても理由をコードから導いた。** 条件 B の sonnet は3回とも、`lstatSync` が `ENOTDIR` を投げることを、`try/catch` を残す理由に挙げた。作者のコメントと同じ理由である。うち1回は「コードを読んだ推定で、実行はしていない」と書いた。
- **コメントが無いと、挙げる理由がずれることがあった。** 条件 B の haiku は、3回のうち2回で、権限のエラーを理由に挙げた。残すという結論は同じだった。
- **テストがあると、agent はテストを理由に挙げた。** 条件 C の6回のうち3回の報告が、規則を固定するテストがあると書いた。
- **検査が落ちて直す経路は起きなかった。** 条件 C で、14件のテストが agent の変更を落とした回は無かった。
- **`entryExists` の書き換えは、振る舞いを変えなかった。** 3回とも、`throwIfNoEntry: false` と `!== undefined` を外し、例外の有無で判定する形にした。
- **どの回も、同じ箇所を削った。** 18回のうち15回が `builtinTests` の `.sort()` を外した。関係するテストは通った。
- **新しいコメントは足されなかった。** 条件 A の6回のうち5回は、既存のコメント1行を書き換え、1回は消した。条件 B と C では、コメントは0行のままだった。
- 1回の所要時間は134秒から493秒、費用は18回の合計で5.60ドルだった。

確かめていないことは次のとおりである。

- **コードから読み取れない理由。** `E01` と `P01` の理由は、Node.js の API の知識で導ける。「Bun は名前が `.` で始まるテストファイルも実行する」のような外の事実を、コメント無しで agent が守るかは測っていない。
- **コードと食い違うコメント。** 古いコメントに agent が従うかは測っていない。
- **コードを足す作業。** 今回はコードを削る作業だけで、agent がコメントを写して増やすかは測れていない。
- **回数。** 条件とモデルの組ごとに3回である。
- **rules の無い環境。** 利用者の rules を読み込まない agent では、測っていない。

## 見直す条件

- 外の事実を述べるコメントを消した条件で計測したとき。
- コードと食い違うコメントを置いた条件で計測したとき。
- モデルか Claude Code が更新されたとき。
- feedback-loop のコメントの検査が、採用または却下されたとき。
