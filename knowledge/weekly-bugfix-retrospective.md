# 直近 1 週間のバグ修正を並べ、「ゼロから作り直すなら何を変えるか」を agent に問う

## TL;DR

- 1 週間分のバグ修正の PR を並べて、「ゼロから作り直すなら、どんな設計の判断をすれば、これらの問題がそもそも起きなくなるか」を agent に問うと、個々の PR では流れていた穴が、同じ設計の問題として見えた。
- 開発ハーネスの repo（dotclaude）で試した。マージした 77 件のうち、バグ修正は 12 件だった。12 件は 4 つの原因にまとまり、精査の後に Issue 4 件になった。
- いちばん大きい発見は、公開の関門がコマンドの文字列の解析に頼っていることだった。同じ解析器の見逃しが 1 日に 3 件あり、測ると 29 通りの書き方のうち 16 通りが通った。
- agent の最初の提案は、そのままでは使えなかった。4 日前の持ち主の決定と食い違う案が 1 つあり、4 つのまとまりのうち 2 つは、コードを読むと Issue にする理由が無かった。
- 1 つの repo で 1 回試しただけである。かかった時間と費用は測っていない。検証日は 2026-11-23、モデルは `claude-fable-5-2` と `gpt-6.2-astra`。

## 結論

バグ修正が続いている repo では、週に 1 度、この振り返りを行う。agent の答えは提案として扱い、過去の決定との照合、実際の測定、コードでの精査を通してから Issue にする。今回は 12 件で、まとまりが作れた。何件から作れるかは分からない。

## 採用した理由

| できるようになったこと | 根拠 |
| --- | --- |
| 個々の PR に散った「直さなかった懸念」を、1 つの問題として扱う | 解析器のバグ修正 3 件（#872、#874、#876）は、それぞれの PR の本文に、まだ残る穴を書いていた。3 件を並べるまで、解析に頼る作りそのものは問われなかった |
| 修正の件数ではなく、原因の数で見る | 12 件は、4 つの原因と単発 1 件にまとまった。4 件は子プロセスの扱い、3 件は文字列の解析、2 件は検証の記録、2 件は写しの食い違いだった |
| 目標に照らして、どれが重いかを決める | repo の `OUTCOME.md` を一緒に渡した。文字列の解析の問題は、目標の 1 つ（agent が関門を迂回できない）に直接関わるので、最初に扱った |
| 論じる代わりに測る | 関門に 29 通りの書き方を渡して数えた。結果は [command-string-gate-misses-publish-spellings.md](command-string-gate-misses-publish-spellings.md) に書いた |

きっかけは、[Steve Ruiz の投稿](https://x.com/steveruizok/status/2124233664326467953)である。投稿のリプライには、「直近の作業に寄りすぎて、長期の目標に合わない助言が返ってきた」という報告がある。今回は、目標を書いた文書を渡し、寄りすぎていないかを agent 自身に確かめさせた。渡さなかった場合とは比べていない。

## 却下した案

| 案 | 却下した理由 |
| --- | --- |
| agent の提案を、そのまま Issue にする | 最初の案（公開を host のプロセスに戻す）は、持ち主が 4 日前に決めた方向（主役は対話の session、関門は hook と単体の script）と食い違っていた。食い違いは、Issue を書く前に過去の Issue を読んで初めて分かった。同じ読み落としで、決めた段取り（関門は記録だけの設定で入れ、誤検出を見てから止める）を、弱点として報告していた |
| 4 つのまとまりを、全部 Issue にする | 2 つは、コードを読むと理由が無かった。子プロセスの扱いは、置き換える予定の経路の話で、残る側はすでに揃える作業が進んでいた。検証の記録は、区別しなくても関門を誤って通す方向に働かなかった |
| 1 つのモデルの読みだけで決める | 別のモデルに同じ材料で独立に答えさせると、まとめ方はほぼ一致した。差が出たのは対策の側である。事故の防止にしかならない案を保証として扱っていたこと、直す順番によって正当な手順が止まることは、相手の反論で分かった |

## 検証

| 項目 | 内容 |
| --- | --- |
| 検証日 | 2026-11-23 |
| モデル | `claude-fable-5-2`（振り返り、測定、精査）、`gpt-6.2-astra`（独立した読みと反論） |
| ツール | thkt/dotclaude の main `88d141c8` から `4c0714e8`、`gh` CLI、Claude Code 2.1.330 |

### 再現手順

1. 期間のバグ修正の PR を集める：`gh pr list -R <repo> --state merged --search 'merged:>=<7 日前の日付>' --limit 200 --json number,title,body,files`。題が `[Bug]` や `fix` で始まるものを選ぶ。

2. PR の本文から、変えたこと、原因、直さなかった懸念を取り出す。差分ではなく本文を使う。

3. repo の目標を書いた文書（`.claude/OUTCOME.md`）を用意する。

4. agent に、次の形で問う。

   ```text
   直近 1 週間のバグ修正を見て。このプロジェクトをゼロから作り直すなら、
   どんな設計の判断や機能の調整をすれば、これらの問題がそもそも起きなくなるか？

   - 共通の原因ごとにまとめ、どの PR が入るかを書く。1 件だけのまとめは「単発」と書く
   - まとめごとに、今のコードのどこをどう変えるかが分かる設計の判断を書く
   - 判断ごとに、費用、失うもの、目標・Non-goals・Constraints と合うかを書く
   - 直近の 1 週間に寄りすぎていないかを確かめる
   - 読んで確かめたことと、推測を分ける
   ```

5. 別のモデルに、同じ材料と同じ問いを渡し、相手の答えを見せずに答えさせる。2 つを突き合わせる。

6. いちばん重いまとまりを、実際に測る。今回は、関門に書き方を変えた入力を渡して、通る数を数えた。

7. 対策を決める前に、その部分を作った過去の Issue と決定の記録を読む。提案が過去の決定と食い違うときは、食い違いを示して持ち主に聞く。

8. 残りのまとまりを、コードで確かめる。今も問題が残っているか、ほかの作業が同じ所を直していないか、放置すると何が起きるかを見て、Issue にするかを決める。

### 結果

| 段 | 結果 |
| --- | --- |
| 集める | マージした PR 77 件、うち `[Bug]` は 12 件 |
| まとめる | 4 つの原因と単発 1 件。2 つのモデルのまとめ方は、ほぼ一致した |
| 測る | 公開の関門は、29 通りの書き方のうち 16 通りを通した |
| 過去の決定と照合する | 最初の対策の案が、4 日前の決定と食い違った。持ち主に聞き、決定を保つ形（session が公開の script を呼ぶ）に変えた |
| 精査する | 4 つのまとまりのうち、Issue にしたのは 2 つ。2 つは見送った |
| Issue にする | 4 件（[dotclaude#948](https://github.com/thkt/dotclaude/issues/948)、[#949](https://github.com/thkt/dotclaude/issues/949)、[#950](https://github.com/thkt/dotclaude/issues/950)、[#951](https://github.com/thkt/dotclaude/issues/951)）。うち 1 件は、実装の前の調査である |

精査の途中で、バグ修正には出ていなかった穴も見つかった。関門は Bash の tool だけを見るので、PR を作る MCP の tool は関門を通らない。

確かめていないことは 3 つある。Issue 4 件は、まだ実装されていない。振り返りで見つけた問題が、次の週のバグ修正を減らすかは分からない。目標の文書を渡さなかった場合に、答えがどう変わるかは試していない。

## 見直す条件

- 2 回目以降の振り返りで、新しいまとまりが出なくなったとき。間隔を空ける。
- Issue 4 件が実装され、次の週のバグ修正の原因を数えられるようになったとき。効果をこのページに足す。
- バグ修正が週に数件しかない repo で試したとき。件数が少ないと、まとまりが作れない可能性がある。
