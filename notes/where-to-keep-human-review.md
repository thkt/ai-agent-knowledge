| 変更の種類 | 戻せるか | すぐ気づけるか | 見る人が判断できるか | 中核か | 軸の上での位置 |

| 出来事で起きる agent の設定 | 戻せる | 気づきにくい。指示に反して書き込んでも、報告には出ない | できる | 中核である。権限に関わる | 読む側 |

この当てはめから、3 つのことが言える。次は、筆者の推測である。

- **開いている PR がたまるのは、軽い側と読む側を、同じ重さで扱っているためである。** `sources/` の頁は、軸の上では、CI が通れば merge してよい側に入る。
- **手元で重いのは、2 番目の軸である。** 決まりの変更も、導入先へ配る変更も、戻せるが、気づくのが遅い。同じ日に、導入先で先に走らせることを選んだのは、この軸への手当てに当たる。
- **3 番目の軸は、数えていない。** agent の指摘を thkt が採った割合と、thkt が読める量は、どちらも測っていない。

## Kinopee の 3 分野を、手元に当てる

Kinopee の 3 分野（認証と権限、課金と決済、データベース）は、1 番目の軸と 4 番目の軸が重なる所だ、と筆者は読んだ。手元の repo は、課金とデータベースを持たない。同じ位置に来るのは、次の 2 つだと考える。これも、筆者の推測である。

- 権限に関わる設定。agent のモード、ブランチの保護、出来事で起きる agent の条件である。
- 外へ出る操作。Issue と PR の公開、導入先への配布、非公開の内容を含みうる報告である。

## 分かっていないこと

- 軸が 4 つで足りるか。投稿は、個人の整理として挙げている。
- 軸で分けて運用したときに、見逃しが増えるか。投稿にも、手元にも、数字が無い。
- 軽い側の PR を読まずに merge したときに、頁の誤りが残る割合。
- Kinopee の bot の判定が、人の判断とどれだけ一致するか。

## 検証したら

- 軽い側の PR を、決めた条件で merge する運用を試したとき。後から見つかった誤りの数を数え、`knowledge/` に書く。
- agent の指摘を採った割合を数えたとき。3 番目の軸の行を、数字で書き直す。
- 4 つの軸に入らない資料を、もう 1 件読んだとき。「入らなかった話」の節を見直し、軸を足すかを決める。
