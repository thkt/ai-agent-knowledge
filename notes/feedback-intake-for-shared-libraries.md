# 共有の部品への要望を、報告する側で集める入口の、当てはめ先 2 つ（2026-11-23）

マネーフォワードの発表（[design-system-feedback-loop-moneyforward.md](../sources/design-system-feedback-loop-moneyforward.md)）の「報告する側の環境で、agent に情報を集めさせる」を、2 つの場面に当てはめて考察した。1 つは自分の道具とその導入先、もう 1 つは仕事で扱う共有の UI の部品である。どちらも試していない。

## TL;DR

- 発表の芯は、情報がある場所で情報を集めることである。この形は、共有の部品を複数の利用先が使う構造なら、当てはまる。
- 自分の道具（feedback-loop と dotclaude の plugin）と導入先は、同じ構造を持つ。入口は無く、導入先の版と設定は、agent が後から手で読んでいる。
- 自分の道具に当てるときの制約は、公開の repo に、非公開の導入先の名前、コード、ログを書けないことである。入口は、集めた内容から、それらを外す段を持つ必要がある。
- 仕事の共有の UI の部品に当てるための材料は、手元に無い。利用先の数、要望の届き方、過去の判断の置き場所を、先に確かめる。
- 先に手で回す。thkt/feedback-loop#253 の実装後に行う、導入先 2 つでの確認が、最初の回になる。

## 発表から取る形

次の 3 点は、発表の資料の記述である。

- 利用者の側で動く skill が、利用の状況を調べ、質問と誤用を解決し、残ったものを Issue にする。
- トリアージの agent が、過去の Issue と設計の資料を引いて、対応するかを決める。
- 効果を、解決までの時間と、人の返信の数で、移行の前後で比べる。

次の 1 点は、筆者の推測である。

- 人の返信が減ったのは、聞き返しが減ったためである。版、使い方、再現の条件は、利用者の repo にあり、そこで動く agent なら読める。資料は、返信の数と課題を別の頁に書き、2 つをつなぐ説明は書いていない。

## 当てはめ先 1：自分の道具と、その導入先

### 構造が同じである根拠

| 発表の構造 | 手元の対応 | 基づくもの |
| --- | --- | --- |
| 共有の部品（MFUI） | feedback-loop、dotclaude の plugin | 手元の資料 |
| 利用するプロダクト | 導入先の repo。公開のものと、非公開のものがある | 手元の資料 |
| 報告の経路（Slack） | thkt が導入先で気づき、agent との会話で伝える | thkt の発言 |
| 報告する側の skill | 無い | 手元の資料 |

thkt は 2026-11 に、導入先での利用の状況は拾えないが、自分のプロジェクトに入れて回すことはできる、と述べた。

### 入口が無いことで起きたこと

次の 2 件は、同じ日の作業の記録である。

- 導入先の 1 つ（thkt/dotagents）は、テストを自前のスクリプト越しに動かしている。この設定は、乗り換えの Issue（thkt/feedback-loop#253）を書いた後に、agent が導入先の設定ファイルを手で読んで分かった。
- 導入先に入っている feedback-loop の版は、導入先の生成物の記録を読むまで分からなかった。

### 入口の形（筆者の推測）

1. 導入先の repo で動く手順を、道具の skill に足す。
2. 手順は、入っている版、設定、失敗した実行の出力を集める。
3. 手順は、契約の文書を読み、使い方の誤りなら、その場で直し方を示して終わる。
4. 残ったものを、上流の Issue の下書きにする。起きた日と、導入先での所在を書く。
5. 人が下書きを読み、公開するかを決める。

4 番目は、thkt/dotclaude#959 の根拠の行とつながる。導入先で起きたことを、日付と所在つきで集めるので、`観測` の行が書ける。週ごとの集計では、出どころが利用の Issue として数えられる。

### 制約

- **公開の repo に、非公開の導入先の名前、コード、ログを書かない。** feedback-loop の repo は、これを制約に置く（thkt/feedback-loop#253 の「repo の方針が課す手順」の表）。入口は、集めた内容から、名前とコードを外す段を持つ必要がある。外した後に、再現に足りる情報が残るかは、分からない。
- **agent が持ち込む報告が、増える。** 入口の agent が「気づいたこと」を足すと、利用で起きていない要求が混ざる。#959 の「実際には起きていない」の問いを、下書きの段で通す必要がある。

### 進める順（筆者の推測）

`sources/toyota-production-system.md` の頁（この repo の PR #31 で足す）は、機械を作る前に手作業でやる、と書く。この順に従う。

1. #253 の実装後に、導入先 2 つで検査を走らせる。この確認は、#253 が thkt に引き継いでいる。
2. そのとき、上流に伝えた事柄ごとに、何を集めたか、何を聞き返したかを記録する。
3. 3 回たまったら、集めた項目が毎回同じかを見る。同じなら、手順を skill にする。

## 当てはめ先 2：仕事で扱う、共有の UI の部品

### 当てはまる条件（筆者の推測）

発表の形が効くのは、次の 3 つがそろうときだと考える。

- 1 つの共有の部品を、2 つ以上の利用先が使っている。
- 要望が、版、使い方、再現の条件を欠いた形で届いている。
- 対応するかの判断が、過去の経緯を知る人に寄っている。

### 手元に無い材料

仕事の側については、次のどれも確かめていない。この頁には、組織、案件、人の名前を書かない。

| 確かめること | 分かると決まること |
| --- | --- |
| 共有の部品が、いくつの利用先で使われているか | 入口を作る価値があるか。利用先が 1 つなら、要らない |
| 要望が、どの経路で届くか（チャット、表、口頭） | 入口を、どこに置くか |
| 利用先の repo で、agent を動かせるか | 報告する側で集める形が、取れるか |
| 過去の設計の判断が、どこに書かれているか | トリアージの agent に、何を読ませるか。書かれていなければ、先に書く |
| 要望から対応までの今の時間と、往復の数 | 効果を、前後で比べられるか |
| 利用先に、外へ出せない情報があるか | 集めた内容から、何を外すか |

### 仕事の側で、先に取れる形（筆者の推測）

- **測ることから始める。** 発表の指標（解決までの時間、人の返信の数）は、仕組みを変えなくても数えられる。先に今の値を取ると、後で比べられる。
- **下書きまでにする。** thkt は同じ日に、仕事の repo で agent が行うのは、ローカルでの下書きまでがよい、と述べた。入口が作るのは Issue の下書きで、公開は人が行う。
- **出来事で起こす形は、既にある道具で組める。** `sources/mcp-events-extension.md` の頁（この repo の PR #29 で足す）に、Issue が開かれたら agent を起こす試しを書いた。チャットの製品も、同じ月に、出来事と時刻で agent を起こす機能を発表した。要望がチャットに届くなら、入口をそこに置ける。

## 分かっていないこと

- 発表の 0 段の skill が、何を調べ、何を聞くか。
- 対応しない、と決める基準。
- 非公開の導入先の情報を外した後に、報告として足りる情報が残るか。
- 入口を置いたときに、報告の数が増えるのか、減るのか。

## 検証したら

- 当てはめ先 1 は、手で 3 回回した結果を `knowledge/` に書く。
- 当てはめ先 2 は、「手元に無い材料」の表を埋めた結果を、組織と案件の名前を除いて、この頁に足す。
