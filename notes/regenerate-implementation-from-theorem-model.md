# 定理モデルを正として実装を定期的に作り直す仕組みの、利点と課題（2026-11-19）

社内で聞いた PoC の構想について、利点、課題、人間と機械の分担を考察した。PoC の中身は確かめておらず、手元で試してもいない。

## TL;DR

- PoC の構想は、既存の実装から定理モデルを起こし、モデルを正として実装を捨てては作り直すものである。
- 筆者の推測では、利点は、コードの劣化が溜まらないこと、作り直しで挙動を落としにくいこと、大きな変更を作り直しで済ませられることである。
- 課題は4つある。現実装をそのまま正とすること、定理が欲しい性質を書いているか、作り直した実装がモデルに合っているかの判定、モデルの外の挙動が消えることである。
- 人間の判断は無くならない。判断する対象が、作り直される実装からモデルの差分に移る。
- PoC がモデルを何で書くかと、適合をどう判定するかは確かめていない。

## PoC の構想

PoC の担当者の発言は次の2件である。

- 実装を定理モデルにし、既存の実装を捨てて実装し直す。
- 実装そのものに寿命を持たせ、定期的に自律的に作り直す。

確かめていないことは次の2つである。

- 定理モデルを何で書くか。Lean などの証明器を使うのか、仕様を書くだけなのかは分からない。
- 作り直した実装がモデルに合っていることを、どう判定するか。

筆者の読みでは、インフラの immutable infrastructure をアプリのコードに持ち込む発想である。immutable infrastructure では、サーバーにパッチを当て続けず、定義から作り直す。この構想では、コードを直しながら使い続けず、モデルから作り直す。

## 利点

PoC の担当者が述べたのは、定期的に作り直すという目的だけである。下の表の利点は、どれも筆者の推測である。

| 利点 | 筆者の推測 | 推測の材料 |
| --- | --- | --- |
| コードの劣化が溜まらない | コードには、回避策、古いパターン、古い依存が溜まる。定期的に作り直せば、溜まった分がそのたびに消える | [poteto の講演](../sources/all-code-is-slop-poteto-talk.md)は、回避策やアンチパターンが確立したパターンに見え、次の agent がそれを写すと述べる |
| 作り直しで挙動を落としにくい | 書き直しは、コードの中でだけ決まっていた暗黙の挙動を落としやすい。モデルがその挙動を書き出していれば、新しい実装がモデルを満たすかを機械で確かめられる | [mizchi のプレイブック](../sources/formal-methods-playbook-mizchi.md)は、実装から暗黙の挙動を抜き出す手順を示す |
| 大きな変更を作り直しで済ませられる | 依存の更新、フレームワークの移行、高速化を、モデルを変えずに実装の作り直しで済ませる | [Lean の投稿の digest](../sources/lean-proved-sql-optimizer-post.md)の読みでは、SQL のオプティマイザの書き換えで、証明は「結果が変わらない」根拠として働いた。投稿自体はそこまで書いていない。依存の更新とフレームワークの移行に広げたのは、筆者の外挿である |

## 課題

### 1. 現実装をそのまま正とする

既存の実装からモデルを起こすので、最適でない挙動もバグも、そのままモデルに入る。その結果、作り直すたびに同じバグが再現される。

対策の候補は、mizchi のプレイブックが示す仕分けである。モデルから反例が出たら、ドメインを知る人に「これは意図した挙動か」を尋ねる。意図した挙動なら仕様として書き、そうでなければバグとして直す。

この仕分けには、意図、課題、ドメイン知識を合わせて判断する人間が要る。モデルを起こしたときの仕分けは1回で済む。一方、要件が変わるたびにモデルの差分が出て、人間はその差分を判断し続ける。

### 2. 定理が欲しい性質を書いているか

PoC が Lean を使うかは確かめていない。Lean を使う場合、確かめることは2つに分かれる。

| 確かめること | 担い手 | 理由 |
| --- | --- | --- |
| 証明が Lean の検査を通っているか。`sorry` や `axiom` で穴を埋めていないか | 機械 | `#print axioms` が、証明が依存する公理と `sorry` を一覧にする。筆者の知識によるもので、未照合である |
| 定理が欲しい性質を書いているか | 人間 | Lean は、定理の文が欲しい性質であるかを確かめない。誤った定理を正しく証明しても、実装は安全にならない |

### 3. 作り直した実装がモデルに合っているかの判定

証明が保証するのはモデルで、実装ではない。Lean の投稿の著者は、証明をコードに落とす段で agent がバグを入れたと返信している。

自律的に作り直す仕組みでは、作り直すたびに人がレビューするわけではない。そのため、この判定を機械にしないと、作り直しのたびにバグが入りうる。

判定を機械にする候補は2つある。

- **モデルから経路を作り、実装を動かす。** [状態機械の検査の knowledge](../knowledge/state-machine-check-in-app-language.md) では、状態ごとの最短経路では実装の欠陥を拾えず、遷移ごとの経路で拾えた。
- **実システムの操作ログをモデルに照らして再生する（trace-checking）。** mizchi のプレイブックの digest は、この方法で食い違いを見つけた事例と、実用的でなかった事例の両方を照合した。

### 4. モデルの外の挙動が消える

モデルに書いていない挙動は、作り直すと消える。たとえば、性能、エラーの文言、UI の細かい動きである。

このうち文言や CSS のような細部については、消えてもよいと判断する材料がある。[Dave Kiss の投稿](https://x.com/davekiss/status/2123035173847441868)（2026-11-18）は、stably_ai の Orca が agent に出す指示を紹介する。agent は既定ではテストを足さず、足してよいのは変更を revert すると落ちるテストだけである。文言、CSS クラス、定数を確かめるテストに触れたら、更新せずに削除する。この指示は投稿の記述によるもので、Orca の実物は確かめていない。

筆者の読みでは、この基準はモデルに入れる挙動を選ぶときにも使える。revert しても落ちないような細部は、モデルに入れず、作り直しで消えるに任せる。性能はこの材料の範囲外で、消えてよいかは別に判断が要る。

## 人間と機械の分担

この節は筆者の推測である。「現実装をもとに最適な方法を導く」には、性質の違う仕事が混ざっている。分けると、4つの仕事のうち、人間が要るのは2つになる。

| 仕事 | 担い手 | 理由 |
| --- | --- | --- |
| 現挙動を抜き出して反例を出す | 機械 | mizchi のプレイブックの手順で機械的に進められる |
| 反例が意図した挙動かを判定する | 人間 | 意図、課題、ドメイン知識を合わせた判断が要る。ただし、具体的な反例1件に yes か no で答える作業なので、白紙から要件を書くより軽い |
| どう作るか（実装の最適化） | 機械 | モデルを満たす範囲なら、機械が探せる。Lean の投稿では、agent が証明付きの最適化を4つ足した。投稿者の要約によるもので、証明が Lean の検査を通ったかは書かれていない |
| 何を満たすべきか（振る舞いの最適化） | 人間 | モデルを変えることであり、要件定義そのものである。作り直しの仕組みの外にある |

この仕組みは人間の判断を無くさない。判断する対象を、コードからモデルに移す。人がレビューするのは、作り直される実装ではなく、モデルの差分になる。

## 見直す条件

- PoC がモデルを何で書くか、適合をどう判定するかが分かったとき。
- PoC に、課題1の仕分けの段と、課題3の判定の段があるかが分かったとき。
- 手元で、モデルから実装を作り直す仕組みを試したとき。結果は `knowledge/` に書き、このページを根拠として引く。
