## 中心の主張

**作る前に「良い状態」を eval として書けば、モデル、retrieval、構成の選択は議論ではなく試験になる。** 記事は eval を、入力を与え、agent の振る舞いを見て、許容できたかを採点する試験と定義する。golden は、入力と、起きるべきこと、起きてはいけないこと、良い状態の姿の組である。eval が無いと各選択が意見で決まり、いちばん目立つデモが勝つと書く。

## 考え方と根拠

| 考え方 | 記事の記述 | 記事が挙げる根拠と照合の結果 |
| --- | --- | --- |
| 1回の実行ではなく、合格率で読む | 同じ入力でも、言い回し、選ぶ道具、道具の順番が変わる。新しい case は3回回し、結果が割れたら不安定として5〜10回に増やす。重大な case は最初から10回回す | 根拠は説明用の例（同じ case を5回回して3回合格）で、測定は無い。回数の基準に出典は無い |
| case は、実際の失敗と利用者の文面から作る | 仕事ごとに、すべきこと、してはいけないこと、壊してはいけない既存の振る舞いの3種を置く。本番で漏れたバグは case に足す。調整に使わない hidden set を残す。生成した case は、実際の case が集まるまでの足場として使う | 根拠は説明で、数字は無い。十分かどうかは件数ではなく、新しい種類の誤りが出なくなったかで判断すると書く |
| 規則で書けるものはコードで確かめ、読まないと分からないものだけを LLM で採点する | コードは、呼んだ道具、引数、副作用（記録が実際に作られたか）、引用の有無を確かめる。採点器の偏りとして、提示順、長さ、自分と同じ系統の書き方への好みを挙げる。対策は、両方の順で採点する、短い良い例と長い悪い例を並べる、別の系統で採点する、の3つである | 偏りと対策の段落に出典は無い。[llm-evals-makarevych.md](llm-evals-makarevych.md) が、同じ3つの偏りの論文を照合している |
| 採点器は、known-bad の会話を全部落とせると確かめてから gate に使う | 採点器は、対象のモデル以上の能力を持つべきだと書く。根拠に、小さい採点器が known-bad の11件のうち4〜5件を見逃した例を挙げる | **原文と食い違う。** 出典は Red Hat Developer の記事の「Known bad conversations」の節である。known-bad の会話が11件であることと、Llama-4-Scout-17B-16E が4〜5件を見逃したことは一致する。記事は Level 3 で「別の系統の大きいモデルは見逃さなかった」と書く。原文で11件を全件捉えたのは llama-3-3-70b-instruct-w8a8 で、同じ Llama の系統である。原文は、このモデルも1つの指標で断続的に誤検出すると書く。別の系統の Gemini Flash 2.5 については、一覧の外にある微妙な問題を3件見つけたとだけ書き、11件の結果は書いていない。同じ原文の費用の節によれば、そのチームは同じモデルを agent と採点器の両方に使う |
| 道筋が自由なら結果で、手順が要件なら手順で gate する | 資格の確認、取り消せない操作の前の確認、安全確認の順番は、手順を gate にする。trace は常に保存し、失敗した trace を次の case にする | 根拠は説明用の例である |
| 版の比較は、平均ではなく反転で読む | 同じ case で新旧を走らせ、合格から不合格に反転した case を数える。リリースを止めるのは、固定した baseline に2回続けてはっきり負けたときだけにする | 根拠は、道具の説明が広すぎて how-to の質問まで ticket にした例1件で、出典は示されない。「60件で4件以上の純減」という閾値に、統計の根拠は示されない |
| eval でモデル、retrieval、構成を選ぶ | 同じ case、同じ採点器で比べ、費用と遅延も採点の項目にする。retrieval の設定は1つずつ変える。複数の agent への分割は、分割で直る失敗のパターンを eval が示してから行う | 根拠は説明用の例である。小さいモデルが大きいモデルに2〜3点差まで迫るという数字に、出典は無い |
| CI を速さで分ける | コードの検査は commit ごと、採点器は PR ごとと毎晩、長い模擬会話は PR の経路の外で回す | 20件の実行が162秒から18秒になった例は、LangChain の Monday Service の事例にあり、一致する。原文は8.7倍と書き、記事は約9倍と書く |
| 本番の失敗を case に戻す | 返答ごとの guardrail、実際の会話の一部の採点、不確かな case の人の確認、失敗のまとまりの golden 化を回す。規制に近いチームの例として、分類ごとの gate と、境界の probe がリリースを止めることを挙げる | Numan の事例に、分類ごとの採点と、安全の probe の後退がリリースを止めることが書かれている。記事は「そのチームは固定の台本を模擬会話に置き換えた」と書く。原文では、模擬会話は試作の段階で、臨床医が基準を承認するまでリリースの gate にしない |

## 限界

- **本文の数字の大半は、説明用の例である。** 冒頭は、数字を公開されたチームの報告と論文から取ったと書く。しかし「50回中47回」のような例に出典は付かない。出典をたどれたのは、チームの結果として書かれた2件だけである。
- **出典の要約が、原文と食い違う箇所がある。** 採点器の系統と、模擬会話の位置づけである。
- **記事の勧めと、引かれたチームの実践が食い違う。** 記事は別の系統で採点するよう勧めるが、引かれた Red Hat のチームは agent と採点器に同じモデルを使う。
- **参考資料の半分は、eval の道具を提供する側の文章である。** 10件のうち5件は、LangChain、DeepEval、MLflow の記事か文書である。
