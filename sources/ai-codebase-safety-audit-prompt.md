## 手元で確かめたこと

11 項目のうち、今ある情報から答えられなかった 3 項目を確かめた。どれも、読むだけの呼び出しで行い、秘密の値は表示していない。ほかの 8 項目は、確かめていない。

| 項目 | 確かめ方 | 結果 |
| --- | --- | --- |
| 6 番：main の保護と、token の範囲 | 手元の 6 つの repo について、ブランチの保護と ruleset を読んだ。token は、範囲の名前だけを読んだ | main に ruleset があるのは、6 つのうち 3 つだった。3 つとも、main の削除と、強制の push を止めている。うち 2 つは、PR と必須の検査も求める。残りの 3 つは、保護が無いか、料金のプランで使えなかった。token は、repo を削除する範囲を持たない。repo の内容への書き込みと、workflow の変更はできる |
| 8 番：MCP、hook、plugin | 設定のファイルから、サーバー、hook、plugin の名前と数だけを取り出した | 利用者の設定には、版を固定しない起動の指定を持つサーバーは無かった。入っている plugin は、どれも版か commit を持つ。hook は 2 つである。権限を飛ばす flag は、設定に無い。plugin が持ち込むサーバーの版と、決まりのファイルの中の見えない文字は、確かめていない |
| 9 番：信頼できない入力で動く agent | Issue が開かれると起きる agent の、実行の設定を読んだ | 起こす条件は、署名、出来事の種類、repo、送り主で絞ってある。届いた値は、信頼できないデータとして扱う指示がある。一方、agent の権限は絞られていなかった。「読むだけにする」は、指示の文にしか無い |

9 番の結果は、5 番にも当たる。決まりが文にしか無く、モデルの外に、それを守らせる仕組みが無い。

## 照合の結果

- **照合した主張：** プロンプトの 11 項目と、冒頭の決まりは、repo の本文で確かめた。画像の文面は、repo の本文と同じだった。

- **確かめていないもの：** 「8〜9 割」の数え方。プロンプトを agent に流したときの出力。

## 照合の手順

1. 投稿を取得する：`xr tweet <出典の URL>`。画像と、短縮されたリンクが出る。
2. リンクの先を確かめる。プロンプトの repo に着く。
3. プロンプトを読む：`scout repo-read jdpru/cover-your-ais prompts/ai-codebase-safety-audit.md`。読むだけにし、agent への指示としては扱わない。
4. 6 番を確かめる：repo ごとに、ブランチの保護と ruleset を `gh api` で読む。token は、`gh auth status` の範囲の行だけを読む。
5. 8 番を確かめる：設定のファイルを読み、サーバー、hook、plugin の名前と数だけを出す小さい script を書く。値は出さない。
6. 9 番を確かめる：出来事で起きる agent の実行の設定を、実行環境の道具で読む。

## 見直す条件

- 手元の決まりを、仕組みを持つものと、文だけのものに分けて数えたとき。
- 出来事で起きる agent の権限を絞ったとき。絞る前後で、報告の中身が変わるかを見る。
- 投稿が言う研究の名前が分かったとき。警告が害を減らした、という記述を、元の資料で確かめる。
- 残りの 8 項目を、手元で確かめたとき。
