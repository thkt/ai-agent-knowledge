# 「No AI Slop」宣言の考え方と、手元の資料との照合（2026-11）

AIE Code Summit 2026 の登壇者と参加者が、Agile Manifesto の形を借りて、AI の出力を slop にしないための宣言を書いた。宣言は、5つの価値、9つの信念、12の決意から成る。本文を読み、このリポジトリの既存のページと手元の `~/.claude` のルールに照らした。自分たちが採用した判断ではない。

## TL;DR

- 宣言の中心は slop の定義である。作るのにかけた手間が、読む側に理解させる手間より少ないものを slop と呼ぶ。AI を使ったこと自体は条件に入らない。
- 宣言は、根拠も測定も示さない。最後の項で、誰も答えを持っていないと自分で書く。
- 回避策が広がる、次の agent が slop を写す、という主張は、既存の poteto のページと同じである。poteto は宣言の協力者なので、独立した裏付けにはならない。
- 宣言は人のレビューを一部に残すとする。poteto の講演は、agent が自分の PR の大半を merge できるようになると述べる。この2つは食い違う。

## 中心の主張

**slop とは、作る側がかけた手間より多くの手間を、読む側に求めるものである（信念2）。** AI を使ったかどうかは問わない。出力の品質と読む側の体験に責任を持たずに回すと slop になる、とする（信念3）。

5つの価値は「A より B を」の形をとる。作業の量より成果、速さより理解、モデルの初稿より自分の考え、楽な作業より良い作業、出力の手直しより仕組みの改善である。

## 考え方と根拠

番号は宣言の信念と決意の番号である。どの考え方にも、宣言は根拠や測定を付けていない。

| 考え方 | 宣言の記述 | 照合の結果 |
| --- | --- | --- |
| 生成とレビューの手間は釣り合わない | agent の群れは、1人が一生かけてもレビューしきれない量を1日で作る（信念1）。千行の PR や10ページの資料を作るコストはゼロに近づくが、レビューのコストは変わらない（信念5） | 数字は無い。[claude-code-team-verification.md](claude-code-team-verification.md) の記事は、検証の仕組みが agent に任せられる量を決めると書く。宣言の言う非対称を、仕組みの側で埋める考え方にあたる |
| 回避策を重ねると slop が広がる | AI 以前から、問題を正しく解かずに回避し続けると slop が増える。足すことに強く偏った道具からも生まれる（信念6） | [pstack-fix-root-causes.md](pstack-fix-root-causes.md) と [all-code-is-slop-poteto-talk.md](all-code-is-slop-poteto-talk.md) が同じ主張を照合した。どちらも poteto の主張で、poteto は宣言の協力者に名前がある。独立した裏付けにはならない |
| slop は複利で増える | 知識ベース、チャット、コードに slop が溜まるほど、次の agent がそれを読んで写す（信念8）。チームに slop が増えるほど、抗う気力が失われる（信念9） | poteto の講演は、応急処置が広がった例を1件挙げる。[code-comments-for-agents.md](../knowledge/code-comments-for-agents.md) は、agent がコメントを写すかを測れていない。手元で、写された例は集めていない |
| 同じミスが2回出たら、仕組みを直す | 2回目のミスで、仕組みとガードレールを直す。linter、型検査、自動検査で拾えるものは、それに拾わせる（決意12） | poteto の講演の「訂正は rules の行ではなく決定論的な検査にする」と同じ向きである。宣言は「2回」と回数を決めるが、講演は訂正のたびとする |
| 人のレビューを一部に残す | モデルが良くなればコードの大半を読まなくなりうるが、計画、設計、結果のどれかは見る（決意8）。agent のレビュー、linter、検証器だけでは足りない。人が見る範囲は、失敗したときの影響の大きさで決める（決意9） | 範囲の決め方は「影響の大きさ」だけで、基準は示さない。「資料の間で食い違う点」の1を参照 |
| agent が書いたことを明示する | agent が書いたものを送るときは、そのことを明らかにし、重要な部分を確かめてから出す（決意6） | 明示の形（PR の本文、commit の trailer など）は決めていない |
| 確かめていない出力が常に悪いわけではない | 1回のプロンプトや vibe coding は効果の大きい道具である。slop が悪いのは、成果（使える製品、保守できるシステム、自分とチームの時間）を損なうときである（決意11） | 決意1から10の範囲を限る項である。成果を損なうかの判定方法は示さない |
| 量ではなく、使われたかで測る | 何を出し、誰が使い、どう役立ったかが、行数、merge した PR の数、使った token、並列の agent の数より重要である（決意10） | 測り方は示さない |

## 限界

- 宣言は立場の表明で、根拠も測定も無い。最後の項は、誰も答えを持っておらず、受け入れる基準を各自が学び直している、と書く。
- 「手間」を測る方法を示さない。信念2の定義は、作る側と読む側の手間を比べるが、どちらも数えられる形になっていない。
- 署名は gist へのコメントで集める。照合日の gist のコメントは891件で、サイトの署名は714件だった。コメントには署名でないものも含まれうるため、2つの数は一致しない。

## 資料の間で食い違う点

1. **人のレビューをどこまで残すか。** 宣言は、人が少なくとも一部の出力を見続けるとする（決意8、9）。[all-code-is-slop-poteto-talk.md](all-code-is-slop-poteto-talk.md) の講演は、訂正を検査に変えることを繰り返すと、レビューで見る項目が減り、agent が自分の PR の大半を merge できるようになると述べる。同じ協力者が関わる2つの資料で、人が見る範囲の結論が違う。
2. **人の役割が移る先。** [claude-code-team-verification.md](claude-code-team-verification.md) の記事は、人の仕事が、すべての差分を読むことから、完了の定義を決めて証拠を見ることへ移ると書く。宣言の決意8の「計画、設計、結果のどれかは見る」と同じ向きで、食い違いではない。
