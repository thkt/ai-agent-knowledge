# IPA「AI 時代の要求管理ハンドブック」：要求を、目的から運用まで追える形で管理し続ける（2026-11）

IPA（情報処理推進機構）は、要求の定義と管理の考え方、手順、成果物をまとめたハンドブックを PDF で公開している。全 129 頁を読み、手元の進め方（要求を Issue にする手順、根拠の行、Bug の出どころの集計）と突き合わせた。手元の設定は、何も変えていない。自分たちが採用した判断ではない。

## TL;DR

- 中心は、要求を一度書いて終わりにしないことである。要望、要求、要件を分け、目的から要件、テスト、運用の記録までを追える形にし、運用の結果で要求を更新し続ける。
- AI の位置づけは一貫している。AI の出力は候補で、AI の確認はレビューの前処理である。採用、優先順位、リスクの受容、承認は人が行う。執筆時点（2026-10）で、AI だけでの妥当性の判断と承認は確立していない、と書く。
- 手元より細かい点が 3 つある。要求の発生源と根拠を別の項目にする。変更の理由を 3 つに分け、不具合を別に扱う。変更の高さで、戻る工程を決める。
- 手順の効果を測った数字は無い。工数の目安（総費用の 2〜5%）は、出発点として示されている。
- 第 4 章、第 10 章、第 12〜14 章は、複数の部門と委託先を持つ組織が対象で、利用者が 1 人の repo には当てはまらない。照合日は 2026-11-23。

## 中心の主張

**要求の管理は、開発の前の作業ではなく、続ける活動である。** ハンドブックは、要求を目的、要件、設計、コード、テスト、運用の記録と関連付け、変更の理由と影響の範囲を追えるようにすることを、要求管理と呼ぶ（12 頁）。

## 考え方と根拠

### 基礎（第 1〜3 章）

| 考え方 | ハンドブックの記述 | 照合の結果 |
| --- | --- | --- |
| 要望、要求、要件を分ける | 要望は、望みと困りごとである。要求は、実現したいことである。要件は、実現しなければならない事項で、実装と評価につながる粒度で書く。要望から要件へは、直接飛べない（18〜21 頁） | 照合者が読んだ。国際標準は 3 つを別の語で分けていない、とコラムが断る（13 頁） |
| 所与の条件を、そのまま要件にしない | 今ある手順、承認、帳票を、目的に照らして見直す。判断そのものが要るかを先に問う。複雑なまま実装すると、運用、保守、監査が難しくなる（21〜22 頁） | 照合者が読んだ |
| 要求工学の活動は 5 つである | 獲得、分析、仕様化、評価、管理を、繰り返す（24〜26 頁） | 要約で確かめた。5 つの分け方は IPA の整理だと書く |
| 手段で語られた要求は、目的を確かめる | 特定の技術を前提にせず、複数の手段を比べる。手段は、システムと AI に限らない（27〜29 頁） | 原文で確かめた |
| 良い要件の文は、7 つの性質を持つ | 必要、一意、実現できる、検証できる、矛盾しない、粒度が合う、追跡できる。ISO/IEC/IEEE 29148:2018 を引く（29〜30 頁） | 要約で確かめた |
| 要求の台帳は、発生源と根拠を別の項目にする | 項目は、ID、名前、文、種別、発生源、根拠、優先度、状態、関連する要求、検証の方法、履歴、担当、版である。発生源は、要望、法令、会議、ログなどである。根拠は、背景、目的、理由である（32〜34 頁） | 発生源と根拠の 2 行は、原文で確かめた |
| ほかの方法論と組み合わせる | デザイン思考、システムズエンジニアリング、MBSE、アジャイルガバナンスを、要求工学を中心につなぐ。一律に当てはめなくてよい（34〜40 頁） | 要約で確かめた |

| 考え方 | ハンドブックの記述 | 照合の結果 |
| --- | --- | --- |
| 探索する事柄は、4 つを先に決める | 目的、仮説、評価の基準、見直す条件である。目的が変われば、最上流に戻る（49〜50 頁） | 要約で確かめた |
| AI の不確かさを、要件として書く | 確信度が低いときは人に回す。根拠が分からないときは答えない。想定の外の入力では止めて記録する（51〜54 頁） | 要約で確かめた |
| プロンプトは、AI への要求の記述である | 要求工学の一部として扱い、変更の履歴、承認、評価の結果を残す。要件の全体の代わりにはならない（54〜55 頁） | 要約で確かめた |

| 多数の意見と、少数だが重要な兆候を分ける | AI の抽出は、多数に偏る。少数だが重要な候補を「光る原石」と呼び、全体の 1% でも無視せず、人が深掘りする（72〜73 頁） | 原文で確かめた |
| 最初から AI を前提にしない | 規則にでき、同じ入力に同じ結果を求める業務は、AI が要らない場合がある（78〜79 頁） | 要約で確かめた |

## 限界

- **効果の測定が無い。** この手順で手戻りが何割減るかは、書かれていない。工数の 2〜5% は、システムズエンジニアリングの研究からの目安である。
- **想定する組織が大きい。** 経営層、法務、監査、調達、委託先がいる組織を前提にする。第 4 章（グローバル経営、M&A）、第 10 章（調達の単位）、第 12〜14 章（法令と社内規則の構造化）、ReqIF と OSLC は、利用者が 1 人の repo には当てはまらない。
- **AI の研究は、提案の段階のものが多い。** 国際会議の動向のコラムが、実務での有効性は確立していない、と断る（15 頁）。
- **文書が、自分を完成版としていない。** 有識者約 10 名のレビューを経た、更新し続ける文書だと書く（6 頁）。
- **照合の一部は、要約に頼っている。** 23 頁から後ろは、agent の要約を通して読んだ。要約が落とした記述は、この資料に入っていない。

## フローの改善の候補

thkt は 2026-11-23 に、この資料を使って進め方を直していく、と述べた。次は候補で、どれも試していない。上から、変える範囲が小さい順に並べた。

1. **週ごとの集計に、変更の理由の軸を足す。** Bug の Issue ごとに、要求が変わったのか（環境の変化、学んだこと、要求定義の不備）、実装が要求を満たしていないのかを読み分ける。決まりは変えず、数えるだけである。不備の訂正が多い repo は、`/scoping` の問いを見直す材料になる。
2. **#959 の行を、発生源と根拠に分けるかを決める。** 分けると、行が 2 種類になる。先に、根拠の行を手で書く回を重ね、1 行で足りない場面が出るかを見る。
3. **変更の高さを、3 つに分けて戻る先を決める。** 目的が変わる変更は `.claude/OUTCOME.md` へ、要求が変わる変更は `/scoping` へ、手段だけが変わる変更は Issue の中で直す。今は、どの高さの変更かを問う手順が無い。
4. **「実際には起きていない」の問いに、少数の兆候の扱いを書く。** 起きたときの害が大きく、戻せない事柄は、起きていなくても要求になりうる、と問いの文面で示す。

- **照合した主張：** 原文で確かめたのは、発生源と根拠の項目、手段の比較、AI の確認の位置づけ、複数の agent の連携、光る原石、変更管理の節である。

- **範囲外：** 第 4 章、第 10 章、第 12〜14 章の中身は、この資料では表にしていない。

## 照合の手順

1. PDF を取得する。出典の URL を開いて保存する。
2. 本文を取り出す。macOS では、PDFKit の `PDFDocument` で頁ごとの文字列を取り出す小さいプログラムを書き、`swiftc` で作って走らせる。出力は、頁の番号つきの 1 つのテキストにする。
3. 22 頁までを読む。残りは、3 つの範囲に分けて agent に全行を読ませ、節ごとの要約を受け取る。agent には、読む範囲と、外の知識を足さないことだけを伝える。手元の決まりとの関係は伝えない。
4. 要の箇所を、取り出したテキストの検索で確かめる。確かめた語は、`発生源`、`根拠`、`前処理`、`直接上書き`、`光る原石`、`初期要求定義の不備` である。
5. 手元の決まりは、`gh issue view 959 -R thkt/dotclaude` と `gh issue view 253 -R thkt/feedback-loop` で読む。
