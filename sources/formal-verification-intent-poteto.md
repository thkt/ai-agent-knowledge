# 「形式検証は意図への一致を保証するが、意図の正しさは保証しない」という発言（2026-11）

Ray Fernando が X に投稿した動画で、Lauren Tan（poteto）は、形式検証の危険として、モデルとコードのずれと、人が仕様を読まないことを挙げる。動画の音声を文字起こしで読み、このリポジトリの既存のページと、手元で決めた根拠の仕組み（thkt/dotclaude#959、#960）に当てはめた。発言を裏づける測定は無く、自分たちで確かめた判断でもない。

## TL;DR

- 発言の中心は、形式検証は「ある意図に従っている」ことを保証するが、その意図が正しいかは保証しない、というものである。人が仕様を読まなければ、意図の正しさは確かめられない。
- 危険の 1 つ目は、ずれである。検証の言語が元のコードの言語と違うので、モデルが実行時の動きと合っているかが分からない。
- 型も形式検証の一種だ、という説明から始まる。TypeScript の引数と戻り値の型は、機械が「この入力と出力だけが許される」と証明している。
- 同じ 3 つの危険は、手元で 2026-11-23 に決めた「全ての要求に根拠の行を書かせる」仕組みにも当てはまる。意図の正しさを確かめる場所は、持ち主が根拠の行を読むところにしか無い。
- 発言の出どころ（どの対談の一部か）と、動画の長さは確かめていない。照合日は 2026-11-23。

## 中心の主張

**検証が通ることと、検証している内容が正しいことは、別の問題である。** 話し手は、形式検証は万能ではないと述べ、何を証明しているのかをどう知るのか、と問う。誤った前提からは、偽の命題も証明できてしまうからである。

## 手元の仕組みに当てはめたときの差

2026-11-23 に、要求を Issue にする skill が、全ての Issue に根拠の種類と所在を書かせると決めた（[evidence-before-implementation.md](../knowledge/evidence-before-implementation.md)）。thkt は、この仕組みを形式検証になぞらえた。発言の 3 つの危険を、その仕組みに当てた。

| 発言の危険 | 根拠の仕組みでの形 | 当てはめた時点の手当て |
| --- | --- | --- |
| 何を証明しているか分からない | 根拠の行が、必要とは別のことを示す。落ちるテストは「欠陥がある」を示すが、「直す必要がある」を示さない | 一部だけある。落ちるテストと実行の出力を「主張の裏付け」に分け、それだけでは要求にしない。観測の所在は、実在だけを確かめていた |
| 別の言語で書くので、ずれる | Issue と DR は文章で、コードとは別の言語である。feedback-loop の DR-0001 は、accepted になった日に、退けた理由の 1 つが古くなった | 一部だけある。実行の出力は、やり直して確かめられる。文章の前提は、書いた後に確かめる場所が無い |
| 人が読まなければ、意図は確かめられない | 「決定」の根拠は、持ち主が読んで決めたことを前提にする。Issue が長いと、弱い前提が読まれないまま合意になる | 無かった。根拠の行を足すと、Issue はさらに長くなる |

当てはめた結果、2 つを足した。

- **観測が無い要求の問いに、「実際には起きていない」と 1 文で書く。** thkt/dotclaude#959 に入れた。問いに根拠の行を先頭から並べる案と、agent が決めた点を並べる案は、独立した評価を受けて #959 から外し、別の Issue に回した。
- **週ごとの集計に、見張りを置く。** 答えの分かっている Issue 3 件を先に分類し、1 件でも外れたら、その週の件数を信頼できない値として報告する。観測の所在は、実在に加えて、中身が要求を支えているかも見る。

thkt は「意図に従っているかどうかと、意図が正しいかは別の問題である」と述べた。集計と検査は前者だけを見る。後者は、持ち主が根拠の行を読むところに残る。
