## 中心の主張

記事の中心の主張は次のとおり。**最終成果物は証明の山ではなく、「実装の主張・機械検査の結果・ドメインへの確認質問」の台帳である。**

記事は実装を事実上の仕様とみなし、3段で扱う。

1. 実装から、コードが宣言している仕様と、書かれていないが実装が決めている挙動を分けて抜き出す。
2. 抜き出した主張を形式化し、全入力または全順序で成り立つかをツールに攻撃させる。
3. 出た反例を、ドメインを知る人に「これは意図か」と問う。意図なら仕様として明文化し、意図でなければバグとして扱う。

成立を証明できた性質は、回帰ガードとして固定する。反例は、バグ報告であると同時に、仕様の認識を揃える会話の起点になるとする。

記事は外部資料を1件も引用していない。§2 のバグの型については「経験上この型が繰り返し出る」と書く。そのため、下の表の大半の行は、記事が示す根拠が無く未照合である。

## 照合の結果

- **引用：** 記事は外部資料を1件も引用していない。バグの型の根拠は著者の経験である。
- **一次資料と一致したもの：** rename による置き換えの原子性（POSIX.1-2024 の rename）。
- **一部だけ照合したもの：** Z3 を決定可能な断片に収める理由は、非線形の整数算術が決定不能という Z3 の公式ガイドの記述で裏付けられる。区間・集合・等式の組み合わせが決定可能であることは確かめていない。
- **条件が足りないもの：**
  - 「いつか必ず」の検査には fairness の記述が要る。
  - rename は、異なるファイルシステムの間では EXDEV で失敗しうる。クラッシュ後に置き換えが残るかは、rename の節の範囲外である。
  - Z3 は浮動小数点の丸めも扱えるため、「整数演算の丸め誤差だけ」は狭い。
  - trace-checking は、MongoDB Server の事例では実用的でなかった。
- **再現したもの：** 空の AND と OR の値、エラーを false に畳んだ後の否定。
- **照合者が探した arXiv の論文：** 2件とも実在し、題・著者・公開日を API で確かめた。
  - arXiv:2404.16075 "Validating Traces of Distributed Programs Against TLA+ Specifications"（Horatiu Cirstea, Markus A. Kuppe, Benjamin Loillier, Stephan Merz、v1 は 2024-04-24、v2 は 2024-09-17）
  - arXiv:2006.00915 "eXtreme Modelling in Practice"（A. Jesse Jiryu Davis, Max Hirschhorn, Judah Schvimer、2020-05-28）。同じ論文は、MongoDB Realm Sync の operational transformation に対する、モデルからのテストケース生成は成功したと書く。
- **一次資料ではないもの：** fairness の根拠は learntla（Hillel Wayne の解説サイト）で、Lamport の仕様書は読んでいない。
- **照合していないもの：** バグの型が繰り返し出るという頻度の主張、§7 の費用対効果とやめ時、TLA+ や Z3 のモデルを実際に回すこと。
