# shadcn の improve skill が決める、監査の選別と、実行役の報告とレビュー（2026-11）

`improve` は、コードベースを監査し、別の agent が実行する計画を書く skill である。高いモデルを理解と計画に使い、実行は安いモデルに渡す。skill の本文と参考の3ファイルを原文で照合し、手元の `~/.claude` の構成と突き合わせた。自分たちが採用した判断ではなく、手元では動かしていない。

## TL;DR

- 範囲は、監査、選別、計画、実行役の差し戻し、後始末である。手元では、`sweep`、`/think`、`/issue`、`build`、`/preview` に分かれている部分にあたる。
- 参考になるのは、計画の書き方より、subagent の扱いと、実行役の報告とレビューの決まりである。
- 手元に無いと確かめたものは3つある。退けた指摘を次の実行に引き継ぐこと、公開の repo に Issue を出す前の確認、指摘を「今回入れたもの」と「元からあったもの」に分けることである。
- 計画に行番号つきの抜粋を写す点は、手元の `/think` と逆である。手元は、行番号を禁じて、安定した記号で指す。
- 効果の測定は無い。規則は skill の文章で守らせるもので、スクリプトの判定ではない。

## 中心の主張

**計画が成果物である。** skill は、自分を実装者ではなく助言者と定める。高いモデルは、理解、判断、仕様の作成という、知能が積み上がる部分を担う。実行は安いモデルが担う。計画の質が、実行役が成功するかを決めると書く。skill 自身は、ソースを変更しない。書き込むのは `plans/` の下だけである。

### 監査と選別

## 限界

- **効果の測定は無い。** 安いモデルに実行させて成功した割合、差し戻しの回数、退けた指摘の割合は、書かれていない。README の例は、1つの repo での1回の実行である。
- **規則は、文章で守らせる。** ソースを変更しない、範囲の外を触らない、といった決まりは、skill の本文の指示である。判定するスクリプトは無い。
- **行番号つきの抜粋は、コードが動くと古くなる。** skill は、commit の記録と差分の確認で補う。抜粋を更新する手間が、後始末の作業に入っている。
- **実行には、subagent を隔離した worktree で起動できる agent が要る。** できない agent では、計画を人に渡すと書く。
- **計画の置き場所が repo の中である。** `plans/` を commit するかは、利用者に任されている。
