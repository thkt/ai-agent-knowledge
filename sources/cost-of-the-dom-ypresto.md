# ypresto「The Cost of the DOM」：UI のテストの時間を、DOM のエミュレーションと本物のブラウザで分解した発表（2026-11）

LayerX の ypresto は JSConf JP 2026 で、UI のテストを jsdom、happy-dom、Vitest の Browser Mode で走らせ、時間の差がどこから来るかを分解した結果を発表した。スライドの文字起こしを読み、同じ日に手元で行った CI の時間の内訳と突き合わせた。測定は、手元で再現していない。自分たちが採用した判断ではない。

## TL;DR

- 本物のブラウザでのテストは、実時間で jsdom の 1.2〜2.3 倍かかった。CPU の時間で比べると、差は縮むか、逆になる。差の大半は、待ちである。
- 待ちの中身は、フレームである。クリック 1 回に約 3 フレーム（約 50 ミリ秒）かかる。入力の後、Chromium は次の描画まで、返事を受け取らない。
- Chromium の flag を 1 つ付けると、React Aria のテストは 51.4 秒から 39.0 秒になった。発表は、正確さは本物のブラウザが上で、速さは手当てできる、と結ぶ。
- 発端は、agent で PR が増え、CI がマシンを使う量が 2 か月半で約 2.6 倍になったことである。
- 文字の無いスライド 9 枚は、読んでいない。数字の一部は、図から取り出した文字の並びが崩れていて、対応を確かめられなかった。照合日は 2026-11-23。

## 中心の主張

**「本物のブラウザは遅い」は、測ると半分しか当たらない。** 発表は、DOM と描画の処理そのものは小さく、差を作っているのは、操作のたびにフレームを待つことだと示す。

## 考え方と根拠

| 考え方 | 発表の記述 | 照合の結果 |
| --- | --- | --- |
| agent で、テストの基盤が重要になった | monorepo は、月に PR が 5,000 件、パッケージが 100 を超える。CI の core・分は、1 日あたり約 25.6 万（2026 年 9 月の初め）から約 67.7 万（11 月の中旬）になった。UI のテストの job が全体の 24%、Storybook のテストだけで 7.4% を占める | 発表の記述だけである。11 月の値は抽出からの推定で、95% の区間は 64〜72 万だと書く |
| 増えたのは、テストの数である | unit のテストのファイルは 174 から 476、story は 1,121 から 1,478 になった。Storybook と unit の job は、平均 4.9 分から 7.5 分になった | 発表の記述だけである |
| DOM のエミュレーションは、配置と、ブラウザ固有の機能を持たない | happy-dom の DOM は、素の JavaScript のオブジェクトと配列である。幅と高さは 0 を返す。`ResizeObserver`、`IntersectionObserver`、`elementFromPoint`、`scrollIntoView` は、無いか、何もしない。クリックで押せるかは、jsdom も happy-dom も確かめない | 発表の記述だけである。版は jsdom 26.1、happy-dom 21.0.4 である |
| 隔離の強さが、速さを決める | 空のテスト 32 ファイルを 1 worker で走らせた。既定（ファイルごとにプロセスを作る）は 8.94 秒、`vmThreads` は 1.20 秒、Jest は 1.30 秒、Browser Mode は隔離ありで 2.02 秒、なしで 1.38 秒だった | 発表の記述だけである。Vitest 5.1.1 での値である |
| 隔離を切ると、行儀の悪いテストが次のファイルに漏れる | 例は、あるファイルが `HTMLElement.prototype.scrollIntoView` を差し替えると、同じ worker の次のファイルにも残る、である | 発表の記述だけである。環境ごとの表は、列の見出しを取り出せず、どの種類の汚れが残るかの対応を確かめられなかった |
| 実時間では、本物のブラウザが 1.2〜2.3 倍かかる | Mantine（218 ファイル、10,191 テスト）は、happy-dom 14.5 秒、jsdom 17.2 秒、Browser Mode 20.5 秒だった。React Aria（188 ファイル、3,391 テスト）は、happy-dom 20.2 秒、jsdom 21.9 秒、Browser Mode 約 51 秒だった | 発表の記述だけである。4 worker、MacBook Pro（M4 Pro、14 core）での値である。React Aria の Browser Mode の 2 つの値（50.5 秒と 52.7 秒）は、版との対応を確かめられなかった |
| CPU の時間では、差が縮む | Mantine は、jsdom 70.5 秒、happy-dom 59.6 秒、Browser Mode 63.1 秒だった。Browser Mode のほうが、jsdom より 10% 少ない | 発表の記述だけである |
| Vitest の版で、13% 変わった | 5.1.0 までは、新しい iframe が、ソースをファイルごとに約 240 回確かめ直していた。5.1.1 は、キャッシュの指定を付けて、確かめ直しを無くした。Mantine は 23.7 秒から 20.5 秒になった | 発表の記述だけである |
| 差の正体は、待ちである | 1 worker の Mantine で、happy-dom は 74.8 秒、Browser Mode は 124.5 秒だった。上乗せは、iframe の準備が 9.1 秒、ブラウザの待ちが 39.1 秒である | 発表の記述だけである。ほかの区間の値は、対応を確かめられなかった |
| クリック 1 回は、約 3 フレームである | エミュレーションでは、同じ JavaScript の中でイベントを作って配るので、ほぼ 0 ミリ秒である。Browser Mode では、Playwright が、要素が見えていて 2 フレーム止まっていることを確かめてから押す。合わせて約 50 ミリ秒になる | 発表の記述だけである。内訳は推定だと断る |
| 入力の後、Chromium は次の描画まで返事を受け取らない | キーを押した返事は、約 1.3 ミリ秒で出る。Chromium が、次の描画まで task の列を止めるので、テストに届くのは次のフレームになる | 発表の記述だけである。trace で確かめた、と書く |
| flag を 1 つ付けると、24% 速くなる | React Aria で、入力の後も返事を受け取る flag を付けると、51.4 秒から 39.0 秒になった。新しい失敗は 0 件で、4 件が通るようになった | 発表の記述だけである。各 3 回の値である。39.0 秒を、発表は「ポテンシャル」の値と呼ぶ |
| 待ちは、並列の数で埋まる | フレームの上限を外すと、1 worker では 100.5 秒から 90.9 秒になる。4 worker では 23.8 秒から 21.8 秒で、差は 2.0 秒だけである | 発表の記述だけである |
| Storybook は、上乗せが大きい | 同じ操作を Storybook 越しに走らせると、実時間で 14.3 秒、CPU で約 59 秒が上乗せされる。設定だけで 13.1 秒、修正の案を全部入れると 6.6 秒まで減る | 発表の記述だけである。修正の案は、上流には入っていない、と書く |

## 限界

- **測ったのは、1 台のマシンである。** CI の runner での値ではない。
- **題材は 2 つである。** どちらも、コンポーネントのライブラリのテストである。アプリのテストでの値は、示されていない。
- **flag の値は、既定の動きではない。** 39.0 秒は、Chromium の flag を付けた場合である。flag を常用したときの副作用は、書かれていない。
- **失敗したテストの件数を、確かめられなかった。** 文字起こしには、happy-dom で 13 件、Browser Mode で 25 件、という記述が別々の箇所にある。どの題材の、どの段階の値かは、文字起こしからは決められなかった。テストを本物のブラウザに合わせて直した範囲も、分からない。
- **照合は、文字起こしに頼っている。** 図から取り出した文字は、並びが崩れている。対応を確かめられなかった値は、表にそう書いた。

## 照合の結果

- **照合した主張：** 発表の主張は、発表の中の記述だけで成り立っている。外の資料と突き合わせた行は無い。
- **読んでいないもの：** 文字の無い 9 枚。図そのもの。発表の音声。発表が挙げる Chromium のソースと、Vitest の変更。
- **確かめていないもの：** 発表の数字。flag の名前と、今の Chromium での動き。

## 照合の手順

1. 資料を取得する：`scout fetch https://speakerdeck.com/ypresto/the-cost-of-the-dom`。文字起こしが返る。
2. 文字起こしを、スライドの順に読む。図の数字は、ラベルと並んで 1 行に入っている。並びが崩れている箇所は、対応を決めずに「不明」とする。
3. 手元の CI の内訳は、`gh run view <実行の番号> -R thkt/feedback-loop --json jobs` と、job のログの時刻で出す。

## 見直す条件

- 手元か仕事の repo で、UI のテストを本物のブラウザで走らせたとき。待ちと CPU を分けて測り、発表の値と比べる。
- 図を直接読めたとき。対応を確かめられなかった値を、表に足す。
- 発表の修正の案が、Vitest か Storybook の上流に入ったとき。
