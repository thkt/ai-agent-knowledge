# Anthropic「Zero Trust for AI agents」：agent を動かす環境の守りを、3 段の枠組みと 8 段の手順で示す手引き（2026-11）

Anthropic は、自律して動く agent を企業で使うための安全の手引きを、36 頁の PDF で公開している。紹介の頁と手引きの全文を読み、手元の環境（agent の権限、出来事で起きる agent、認証情報）と突き合わせた。手元の設定は、何も変えていない。自分たちが採用した判断ではない。

## TL;DR

- 土台は、ゼロトラストの 3 原則である。信頼せず常に確かめる、侵害された前提で作る、最小の権限。手引きは、これを agent 向けに形を変える。
- 守りの判定は 1 つである。その守りは、攻撃を不可能にするか、面倒にするだけか。面倒にするだけの守りは、agent を使う攻撃者には弱い、と書く。
- 枠組みは 3 段（Foundation、Enterprise、Advanced）で、導入の手順は 8 段である。小さいチームの最低線が Foundation に当たる。
- 手元に当たる記述は 4 つあった。禁止は、指示ではなく権限で行う。信頼できない入力を扱う agent には、sandbox が要る。静的な鍵は、最低線でも認めない。最初に測るのは、気づくまでの時間と、調べた警告の割合である。
- 助言の欄の多くは、自社の製品の機能の紹介である。数字の多くに、出典が無い。照合日は 2026-11-24。

## 中心の主張

**agent の守りは、注意書きではなく、身元、権限、隔離、記録で作る。** 手引きは、今までの権限の管理では、agent が正当な権限を誤って使うことを防げない、と述べる。侵害された前提で、被害の範囲を先に決めておく、という立場である。

## 考え方と根拠

| 考え方 | 手引きの記述 | 照合の結果 |
| --- | --- | --- |
| 守りは、不可能にするか、面倒にするだけかで判定する | 待ち時間の制限、手順の追加、標準でないポートのように、摩擦だけで効く守りは、agent を使う攻撃者には弱い。どの段の勧めも、この基準に置く（4 頁） | 原文で確かめた |
| agent に固有の考慮点は、5 つである | 人の承認なしに進む実行、tool の利用、指示の解釈のあいまいさ、セッションをまたぐ記憶、agent の間の連携（6 頁） | 要約で確かめた |
| 脅威は、5 種類である | 指示の注入、tool と資源の悪用、身元と権限の悪用、供給元と依存、記憶と文脈の汚染（9〜11 頁） | 要約で確かめた。分類は OWASP によるもの、と書く |
| 枠組みは 3 段で、上の段は下の段を置き換えない | Foundation は、小さい展開の最低線である。Enterprise は、ある程度の規模の組織が目指す段である。Advanced は、規制の強い産業と、侵害の影響が重い展開の基準である（13 頁） | 原文で確かめた |
| 静的な鍵と、共有のパスワードは、最低線でも認めない | 期限が分の単位の token を、身元の提供元が発行する形を最低線にする。tool の認証でも、静的な API の鍵は Foundation で認めない（14、26 頁） | 原文で確かめた |
| 信頼できない入力を扱う agent には、sandbox が要る | Web の内容、文書など、信頼できない入力を扱う agent では、隔離は目標ではなく必須だ、と書く（15、16 頁） | 原文で確かめた |
| 禁止は、指示ではなく、権限で行う | 許す行動と禁じる行動を、文書にする。agent に「するな」と言うことと、権限でその行動を禁じることは、別である（24 頁） | 原文で確かめた |
| 被害の範囲を、先に決める | 許す行動、禁じる行動、人に上げる条件、範囲の上限を決めた後で、侵害されたときに何が起きるかを点検する。agent を分けるなら、agent ごとに別の身元と認証情報を持たせる（24、25 頁） | 原文で確かめた |
| 人に上げる条件を、決めておく | 高額の取引、機微なデータ、外との通信を、例に挙げる。危ない tool の呼び出しは、人の確認で止め、承認を記録に残す（24、27 頁） | 要約で確かめた |
| tool は、登録したものだけを許す | 登録の無い tool は拒む。能力を絞る（メールは読むだけ、データベースは構造を変えない）。引数は、agent の側と tool の側の両方で確かめる（26、27 頁） | 要約で確かめた |
| MCP のサーバーは、確かめてから自分で置く | コードを確かめた後に、自前で動かし、自分で署名する。依存は、一覧を持ち、署名を実行のときにも確かめる（23、24 頁） | 要約で確かめた |
| 記憶は、取り出すたびに確かめる | セッションと利用者の間で、記憶を分ける。出どころの印と、改ざんを見つける値を付ける。確かめていない記憶は、期限を短くする（29 頁） | 要約で確かめた |
| 最初に測るのは、2 つである | 異常が起きてから人が気づくまでの時間と、調べた警告の割合。ほかの検知への投資より前に、この 2 つを測る（16、30 頁） | 原文で確かめた |
| 一次調査は agent に任せ、重い判断は人に残す | 証拠の収集、関連づけ、記録は自動にする。封じ込め、公表、顧客への連絡の判断は、人が行う。誤検知の多い規則を 1 つ選び、agent の判定と人の判定の一致を 2 週間測ってから、広げる（32、33 頁） | 要約で確かめた。一致の目安の値は、示されていない |
| subagent は、外からは親と区別がつかない | Claude Code の subagent は、元の agent の延長として動き、元の agent と同じ権限まで持てる。外からの観測と権限の上では、区別が無い（28 頁） | 原文で確かめた |

## 限界

- **自社の製品の紹介が多い。** 助言の欄 21 件のうち、17 件が Claude Code の機能の紹介である。
- **数字の多くに、出典が無い。** 「脆弱性から攻撃まで、数か月から数時間になった」「検知は 1 時間以内」には、根拠が示されていない。出典の付く数字は、注入への対策の効果など、一部である。取り出した文字には、脚注と URL が入っていない。
- **規制との対応は、名前を挙げるだけである。** HIPAA、GDPR、EU AI Act などと整合する、と書くが、条項との対応の表は無い。
- **対象は、企業である。** 証明書、ハードウェアに結んだ身元、記録の集約は、利用者が 1 人の環境には当たらない。
- **手引きは、自分を保証とは呼ばない。** Anthropic の今の考えであり、法務や特定の環境の安全を保証するものではない、と書く（3 頁）。
- **照合は、取り出した文字に頼っている。** PDF から取り出した文字は、表の列が崩れ、語の途中に空白が入っていた。3 段の枠組みの表は、要約を通して読んだ。

## 照合の結果

- **照合した主張：** 判定の基準、sandbox の必須、静的な鍵の扱い、権限での禁止、最初に測る 2 つ、subagent の権限は、取り出した文字で確かめた。
- **読んでいないもの：** 図。表の並び。手引きが挙げる外の資料（OWASP、NIST、各国の指針）。
- **確かめていないもの：** 手引きの数字。助言の欄が挙げる製品の機能の、今の動き。

## 照合の手順

1. 紹介の頁を取得する：`scout fetch <出典の URL>`。本文は、手引きの頁へのリンクで終わる。
2. 手引きの頁から、PDF の URL を取り出して保存する。
3. PDF から、頁ごとの文字を取り出す。取り出した文字は、語の途中に空白が入る。語を探すときは、空白を除いた文字列に対して探す。
4. 全文を agent に読ませ、構成、脅威、3 段の枠組み、8 段の手順、数字、留保に分けた要約を受け取る。
5. 要の箇所を、取り出した文字で確かめる。

## 見直す条件

- 出来事で起きる agent の権限を絞ったとき。手元との関係の表を書き直す。
- 気づくまでの時間か、調べた割合を、手元で測ったとき。
- 手引きが改訂されたとき。3 段の枠組みの最低線が変わったかを見る。
- 3 段の枠組みの表を、照合者が直接読んだとき。
