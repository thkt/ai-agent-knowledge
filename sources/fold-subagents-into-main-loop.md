# サブエージェントを1つの agent のループにまとめる時期を書いた Anthropic の記事（2026-11）

Anthropic の Diane Sarkis の記事は、ルーター、プランナー、ドメインごとのサブエージェントを、スキルとツールを持つ1つの agent のループにまとめ直す時期と手順を書く。記事の全文と、記事が添える移行キットの README を読み、記事が引く数字のうち1つをリンク先で確かめた。手元の `~/.claude` で同じ日に進んだ整理（DR-0129）と突き合わせた。自分たちが採用した判断ではない。

## TL;DR

- 記事の主張は、組織図どおりに分けたサブエージェントより、スキルとツールを必要なときだけ読み込む1つのループのほうが、品質、コスト、レイテンシで勝つことが多い、というものである。
- サブエージェントを残してよいのは、文脈の膨張で性能が落ちると測れたとき、捨ててよい文脈で並列に進めるとき、1つの agent がツールを選び損ねるか指示が矛盾するとき、の3つである。
- まとめる前後は同じ評価で比べ、最終スコアだけでなく、どのタスクの結果が入れ替わったかを見る。各タスクは複数回走らせる。
- 品質と速さの比較（約2倍速い、など）は顧客の事例で、測り方は示されない。Claude Code のシステムプロンプトを80%以上削ったという数字は、リンク先に記述があった。
- 手元の DR-0129 は、同じ向きの整理を使用回数で決め、比べる評価は走らせていないと自分で書いている。

## 中心の主張

**チームごとに作ったサブエージェントは、構成を組織図の写しにする。** 記事は、各チームが自分の agent を作り、中央のチームがその上にオーケストレーターを載せる形を、典型的な失敗として挙げる（Conway の法則）。そこから5つの問題が起きると書く。

- 引き継ぎのたびに詳細が抜ける
- 重複したサブエージェントが、持ち主の無いまま増える
- 各チームが書き足し、システムプロンプトの規則が矛盾する（記事は「フランケンプロンプト」と呼ぶ）
- 評価が部分ごとに閉じ、全体を見る人がいない
- 入れ子のモデルのループが、レイテンシを増やす

代わりに、スキルの説明とツールの説明だけを先に見せ、必要なときに中身を読み込ませる（段階的な開示）。モデルが良くなるほど、ハーネスが担っていた判断をモデルに移せる、という立場である。

## 考え方と根拠

| 考え方 | 記事の記述 | 照合の結果 |
| --- | --- | --- |
| 1つのループは、品質、コスト、レイテンシで勝つことが多い | 複数の企業の導入を比べると、スキルを持つ1つの agent は、単一プロンプトの設計とサブエージェントの設計の両方を品質で上回ることが多かった。ある顧客では、1つのループのほうが約2倍速かった | 未照合。比べ方、件数、タスクは示されない |
| サブエージェントを残してよい条件は3つ | 文脈の膨張で測れる性能の低下があるとき。完了後に捨ててよい文脈で、複数の作業を並列に進めるとき。1つの agent がツールを選び損ねるか、システムプロンプトの指示が矛盾するとき | 記事に記述がある。1つ目は「測れる」ことを条件にしている |
| 残すなら、依存の少ない単位で切る | 他の部分にほとんど依存せず、短い結果を返す作業を割り当てる。独立した調査、明確なインターフェースを持つ部品、ブラックボックスの検証が向く。課題の種類で分けると、伝言ゲームのように精度が落ちる | 記事に記述がある |
| 1つのループの形 | 1つのモデルと1つの文脈でツールを呼び続け、ターン数、費用、書き込みの gate はハーネスで制限する。計画は最初のターンで文脈に書き、結果が出るたびに直す。手順と判断基準はスキルへ、検証や承認の gate のような必ず守る制限はツールへ移す | 記事に記述がある |
| 前提条件と権限はツールの中で確かめる | Y が X の出力を要るなら、Y のツールがそれを確かめ、モデルが読める指示を返す。権限も、ツールが呼んだ利用者の範囲を確かめ、拒否を返す。権限ごとに agent を分けなくてよい | 記事に記述がある |
| ツールは利用者の意図ごとにまとめる | システムプロンプトのツール定義が30〜50個を超えると、選ぶ精度が落ちやすい。API ごとではなく、意図ごとにまとめる | 未照合。数字の出どころは示されない |
| まとめる前に評価を用意する | 中央のチームが全体を通した評価を1つ持ち、各スキルのチームが小さな評価を添える。ゴールデンサンプルは10件で始められる | 記事に記述がある |
| 比べるときは、入れ替わったタスクを見る | サンプルのサポート agent で、サブエージェントを統合するとレイテンシは下がったが、それまで通っていた手順が壊れた。メインの agent が、配送の担当に聞かずに答えた。この問題は2回に1回しか出なかったので、各タスクは複数回走らせる | 記事に記述がある。移行キットの README も「1つのループが常に勝つとは仮定しない。測る」と書き、同じ評価での前後比較で消すかを決める |
| システムプロンプトは削れる | 新しいモデル向けの Claude Code のシステムプロンプトは、80%以上削った | リンク先の記事に「Claude Code のシステムプロンプトの80%以上を削った」という記述がある。何と比べた80%かは、読んだ範囲では確かめていない |
| 道具 | Claude API のスキル群と移行キットが、評価から移行までを助ける。`/skill-doctor` で、スキルごとの費用と使用頻度を見て、要らないスキルを消せる | 移行キットの README は、`/claude-api build-eval`、`hillclimb`、`prompt-audit`、`cost-optimize` と `/skill-doctor` を手順に当てる。手元の Claude Code 2.1.327 の本体に、`claude-api` のこれらの subcommand の名前があった |

## 限界

- 1つのループが勝つという主張の根拠は、顧客の事例と、記事の側が作ったサンプルだけである。件数、タスクの種類、測り方は示されない。
- 記事は Anthropic の製品（Claude Platform、スキル、ツール検索、Claude API のスキル群）を使う前提で書かれている。
- 移行キットは参照実装で、保守も貢献の受け付けもしないと README が書く。

## 照合の結果

- **照合した主張：** 「考え方と根拠」の各行は、記事に記述がある。リンク先と移行キットで確かめた行は、右の列にそう書いた。
