# マネーフォワード「デザインシステムのフィードバックループをほぼ自動化した話」の考え方と根拠（2026-11）

マネーフォワードの MFUI の開発リードが、社内のデザインシステムへの要望を、Issue から PR まで agent でつなぐ仕組みを発表した。日本語版のスライドを読み、手元の流れ（要求を Issue にする手順と、実装の手順）と突き合わせた。仕組みは、手元で試していない。自分たちが採用した判断ではない。

## TL;DR

- 中心は、報告を受ける側ではなく、報告する側の環境で agent に情報を集めさせることである。利用者の repo で動く skill が、利用の状況を調べ、質問と誤用を解決し、残ったものだけを Issue にする。
- Issue の後は、トリアージ、計画、実装の 3 段を agent が進める。各段で、人が確認と承認を挟む。
- 資料が示す結果は 3 つである。解決までの中央値が 3.2 営業日から 1.8 営業日、Slack のスレッドあたりの人の返信が 7.3 から 2.9、人の工数が 2 日から 1 時間になった。工数は体感だと、資料が断る。
- 件数、対応しないと決めた割合、作られた PR のその後は、資料に無い。
- 公開されている資料は、このスライドだけだった。skill の中身と、トリアージの基準は分からない。照合日は 2026-11-23。

## 中心の主張

**共有の部品への要望は、集める場所と判断の材料を変えれば、少ない往復で PR まで進む。** 資料は、要望から調査、分類、計画、実装、リリースまでを、agent と人が分担して進める仕組みとして示す。

## 限界

- **件数が無い。** 中央値と平均が、何件の要望から出たかは、書かれていない。
- **品質の指標が無い。** 作られた PR が、後で直されたか、戻されたかは、載っていない。
- **落とした割合が無い。** 0 段で解決した質問と誤用の数、トリアージで対応しないと決めた数は、載っていない。
- **工数は、測定ではない。** 2 日から 1 時間は、体感の値である。
- **仕組みの中身が、公開されていない。** skill の指示、トリアージの基準、承認の置き場所は、図の粒度までしか分からない。関連する資料を検索したが、この発表を説明する記事は見つからなかった。
- **前後の比較は、ほかの変化を分けていない。** 同じ期間に、チームの人数や要望の種類が変わったかは、書かれていない。
