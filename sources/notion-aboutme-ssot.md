# kyto64「AI ツールごとに前提がずれるので、自分の情報を Notion の SSOT に集約した」の考え方と根拠（2026-11）

kyto64 が Zenn に、自分についての事実とルールの正本（SSOT）を Notion の「ABOUTME」に集め、複数の AI ツールから読ませる運用を書いた。記事の主張を本文で照合し、手元の仕組みと突き合わせた。自分たちが採用した判断ではない。依頼者と照合者の結論は、Notion である必要は無く、使えるのは個人の情報の中身ではなく置き方の型だ、というものである。

## TL;DR

- 記事の主張は、自分についての事実とルールの正本を1か所に置き、各ツールには参照の1行だけを置く、というものである。
- 置き方の型は、入口を1つに固定する、変化の速さでページを分ける、判断のログは消さず状態を変える、ページごとに AI の書く権限を決める、更新のきっかけを決める、の5つである。
- Notion を選んだ理由は、使っている AI のチャットアプリから読めることである。ファイルを直接読む agent には、git で管理する Markdown が合う（依頼者と照合者の判断）。
- 効果は本人の感想で、測定は無い。AI が入口を実際に読み、従ったかを確かめる仕組みは無いと本人が書く。
- 手元には、型の大半がすでにある。無いのは、入口に従ったかを確かめる仕組みである。手元は、それを測るより、守らせたい規則を検査に変える方向をとる。

## 中心の主張

**自分についての情報の正本を、ツールの外の1か所に置き、AI には作業の前にそこを読ませる。** 記事は、AI ツールごとに記憶が閉じているので、ツールが増えるほど自分の説明をやり直し、説明がずれると回答の前提もずれると書く。各ツールの組み込みのメモリは、ほかのツールから読めず、何を覚えさせるかもツールに依存するので、運用として設計しにくいという。

## 考え方と根拠

| 考え方 | 記事の記述 | 照合の結果 |
| --- | --- | --- |
| 入口を1つに固定する | 各ツールの常に読まれる場所（Claude Code のグローバル指示、Codex の AGENTS.md など）に、「作業前に ABOUTME > 00｜Core を読み、回答ルールに従う」という参照の1行だけを置く。全部を読ませると context を大きく消費し、読む順序もツールごとにばらつく | 記述がある。消費量の測定は無い |
| 変化の速さでページを分ける | Core は変化の遅い情報（人物、価値観、回答のルール、今の重点）だけで、四半期ごとに見直す。速く変わる状態は Projects と Decisions のデータベースに置く。Private と Archive は、本人が頼んだときだけ読む | 記述がある |
| 判断のログは消さず、状態を変える | Decisions は追記だけで、古い行は消さず、状態を「撤回」「置換」に変える。撤回された判断も含めて、経緯をたどれる | 記述がある |
| ページごとに AI の書く権限を決める | Decisions は追記してよい。Projects は状態の更新だけ。Core、Career、Build は変更案を出し、本人の承認を得てから更新する。Private と Archive には書かない。会話の要約は書かず、推測を事実として書かない | 記述がある |
| 更新のきっかけを決める | 判断を変えたら Decisions に1行。リポジトリの状態は GitHub から週1回同期し、3か月 push が無ければ「休止」にする。価値観や回答のルールは、本人の承認を得て Core を更新する | 記述がある |
| 正本を AI 同士で共有する | ある AI が Decisions に残した判断や、学びのログの知見を、別の AI が前提として使える。これが最大の効果だと書く | 本人の感想で、測定は無い。同じ Notion に、Grok Bot の bot 群の共通ルールとタスクボードも置いていると書く |

## 限界

- **効果は本人の感想である。** 立ち上げが速くなった、「前に言ったはず」が減った、という効果に、数字は無い。
- **AI が読んだかを確かめる仕組みが無い。** 本人は「強制力はない」と書き、読んだことを前提に検算する場面が残るとする。
- **書き込みの競合を検出できない。** 競合は、更新を本人が頼んだときだけにする運用で避けていて、技術的なロックは無い。
- **機微な情報は、置き場所と既定で読ませない運用で守る。** 暗号化はしていない。漏れて困るものは置かない前提である。
- **Notion と、各ツールの Notion への接続に依存する。**

## 手元の資料との関係（未採用）

この節は、依頼者と照合者が手元の仕組みと突き合わせた結果である。どの設定も変えていない。

**Notion である理由は、チャットアプリから読めることだけである。** 手元の agent（Claude Code、Codex）は、ファイルを直接読む。

| 観点 | Notion | git で管理する Markdown |
| --- | --- | --- |
| 変更の履歴とレビュー | 履歴はあるが、PR でのレビューは無い | diff、PR、commit で追える |
| コピーとの突き合わせ | 仕組みが無い | テストで正本とコピーを照合できる |
| 読ませ方 | 各ツールの Notion への接続に頼る | agent がファイルとして読む |
| チャットアプリの AI からの読みやすさ | 読める | 読めない |

**置き方の型は、手元にほぼある。**

| 記事の型 | 手元の資料 |
| --- | --- |
| 正本は1か所で、各ツールには参照だけを置く | `rules/core/BOUNDARIES.md` の Single Source of Truth は、コピーが残る場合に、正本とコピーを突き合わせるテストまで求める（[BOUNDARIES.md:25-30](https://github.com/thkt/dotclaude/blob/8d15e107/rules/core/BOUNDARIES.md?plain=1#L25-L30)）。記事には、この突き合わせが無い |
| 判断のログは消さず、状態を変える | 手元の DR（MADR）の状態（Accepted、Deprecated、Superseded）と同じ形である。手元の DR は、見直す条件も持つ |
| Core を定期的に見直す | `rules/core/OUTCOME.md` は、6か月ごとに全節を見直すと定める（[OUTCOME.md:37](https://github.com/thkt/dotclaude/blob/8d15e107/rules/core/OUTCOME.md?plain=1#L37)） |
| 入口を固定し、context を節約する | 手元の `rules/` は、`paths:` で、関係するファイルを編集するときだけ読み込む |
| Core の変更は、本人の承認を得てから行う | `rules/conventions/DOCUMENTS.md` は、合意の証拠なしに選択を accepted にしないと定める（[DOCUMENTS.md:40](https://github.com/thkt/dotclaude/blob/8d15e107/rules/conventions/DOCUMENTS.md?plain=1#L40)） |

**無いのは、入口に従ったかを確かめる仕組みである。** 記事にも手元にも無い。手元では、それを測る道具（`/ablate`）を、2026-11-18 の DR-0129 で廃止した。DR-0129 は、廃止で「harness の要素が結果を動かすかを測る唯一の道具」を失うと書き、見直す条件に「harness の要素を測る作業が、手作業で2回行われたとき」を置く（[DR-0129:51、:112](https://github.com/thkt/dotclaude/blob/8d15e107/docs/decisions/0129-retire-review-workflows-reviewer-agents-and-unused-skills.md?plain=1#L51)）。依頼者と照合者は、今は測らないと判断した。守らせたい規則は、文章のまま従ったかを測るより、検査に変えるほうが手元の方向（DR-0129、[all-code-is-slop-poteto-talk.md](all-code-is-slop-poteto-talk.md)）に合うためである。測る意味が残るのは検査に変えられない判断の規則で、決定論的に採点しにくい。
