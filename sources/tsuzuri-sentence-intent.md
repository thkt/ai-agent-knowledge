# tsuzuri の、一文ごとに執筆意図と文機能を記録して AI の文章を読み直しやすくする作りと、手元で試した結果（2026-11）

tsuzuri は、Claude Code に日本語の文章を一文ずつ書かせ、文ごとの執筆意図と文機能を記録するスキルと閲覧アプリである。README とスキルの一部を読み、agent が書いた Issue の本文 1 つに、文機能を付けて読む流れを試した。書かせる流れは試していない。自分たちが採用した判断ではない。

## TL;DR

- 中心の考えは、AI が何を考えてその文を書いたかを文ごとに見える形にすれば、人が読み直しやすくなる、というものである。文を書く前に執筆意図を書かせ、書いた後に文機能（前の文との接続、重要度、役割など）を付けさせる。
- 人やほかの AI が書いた文章にも、文機能と推測した意図を付けて読める。重要度が「核」の文だけを残すと、長い文章の本筋を追える。
- 手元で、agent が書いた Issue の本文に試した。65 文のうち核は 24 文で、字数は 6,152 字（表を含む）から 947 字になった。核の文を通して読むと、その Issue の要点になっていた。
- 弱点が 2 つ分かった。表は文ではなくブロックとして記録され、重要度を持たない。核の印を付けたのは、その本文を書いた agent 自身で、独立した読みではない。
- README は設計の理由ごとに研究を引くが、tsuzuri 自身の効果の測定は無い。引かれた文献は確かめていない。照合日は 2026-11-23。

## 中心の主張

**まとめて生成させた文章は、AI の考えが書き手の手を離れて扱いにくい。文ごとの意図を見える形にすれば、どこがずれているかを、文を指して言える。** README は、tsuzuri を「文章を好みどおりに自動で仕上げる道具」ではなく、「人が読み直しやすい環境を整える道具」と位置づける。

## 考え方と根拠

| 考え方 | README の記述 | 照合の結果 |
| --- | --- | --- |
| 文を書く前に、執筆意図を書かせる | 一文ごとに、その文で読み手に何をするかを先に記述させる。意図を後から付けると、書く前の意図をたどれなくなる | スキルの本文に、同じ決まりがある。記録は同梱のスクリプトだけで作らせ、意図が文より先にあることを、スクリプトが守らせると書く。スクリプトの中身は読んでいない |
| 書いた後に、文機能を付ける | 接続、重要度、役割、工夫、対応する要件の 5 つを付ける | スキルの本文に、5 つの定義がある。接続は 8 類型、重要度は核と衛星の 2 値、役割は 6 分類である |
| 文機能は、正解ではなく目安である | 文の接続や重要度は、人どうしでも判定が一致しにくいと報告されている。読んで違うと思ったら、コメントで直してよい | README の記述だけである。引かれた文献は確かめていない |
| 要件と構成を、先に決める | 書く前に構成を決めると、文章の質が上がったという実験を引く。一方で、主題の質には効果が見られなかったという報告も挙げる | README の記述だけである。効果が分かれることを、README 自身が書いている |
| 核だけを読めば、本筋を追える | 要点だけの要約を読んだ人のほうが、全文を読んだ人より、要点の記憶も推論も優れていたという実験を引く | README の記述だけである。どこまで削ればよいかを数値で定めた研究は見つからなかった、と README が書く |
| 文脈の無い読み手に、読ませる | 書き手は意図を知りすぎていて、読み手がつまずく所に気づきにくい。執筆の文脈を持たない別の AI に、つまずいた箇所を報告させる | README の記述だけである。この流れは試していない |
| 使うほど、初回の質が上がる | コメントで直した文の前後を、AI が次に書く前に読む。言い換えは校正辞書に足される | README の記述だけである。測定は無い |

## 手元で試した結果

2026-11-23 に、agent が書いた Issue の本文（[thkt/dotclaude#959](https://github.com/thkt/dotclaude/issues/959)、149 行）を題材に、人の文を読む流れを試した。

| 項目 | 内容 |
| --- | --- |
| 環境 | Python 3（標準ライブラリだけ）、tsuzuri の main `1ee82cb`。スキルとしては導入せず、clone したスクリプトを直接呼んだ |
| 設定の置き場 | 環境変数 `XDG_CONFIG_HOME` を一時ディレクトリに向けた。`~/.config/tsuzuri/` には書かせていない |
| 記録したもの | 文 65 件と、ブロック 27 件（見出し 15、表 8、箇条書き 3、引用 1）。文ごとに、推測した意図と文機能を付けた |
| かかった時間 | スクリプトの呼び出し 184 回で、15 秒。文ごとの意図と文機能を考える時間は、含まない |
| スクリプトの検査（`check`） | 警告 1 件。段落が 24 あるのに設計書が無い、という内容で、人の文では問題として扱わないとスキルが書く |

核の文だけを取り出した結果は、次のとおりだった。

| | 全体 | 核だけ |
| --- | --- | --- |
| 文の数 | 65 | 24 |
| 字数 | 6,152（表を含む） | 947 |

核の 24 文を通して読むと、その Issue が何を足し、何を足さないかが分かった。末尾の節では、agent が決めた 6 点のうち 4 点と、「最後の版は評価を受けていない」という文が、核として残った。

閲覧アプリも起動し、thkt が核だけの表示を見た。thkt は「良さそう」と述べた。核だけで合意を決められたか、核の付け方に異論があったか、表がどう見えたかの、観点ごとの判断は聞いていない。

## 分かった弱点

| 弱点 | 中身 |
| --- | --- |
| 表は、重要度を持たない | スキルは、見出し、コード、画像、表を、文ではなくブロックとして記録させる。ブロックの文機能は、対応する要件だけである。題材の Issue は表が 8 つあり、決まりの本体が入った表も、細部の表も、同じ扱いになった |
| 核の印を付けたのは、書いた本人である | 題材の本文を書いた agent が、同じ session で、意図を推測し、核かどうかを決めた。核だけで要点が追えたのは、書いた本人が要点を知っていたからかもしれない |
| ブロックには、推測の印を付けられない | 人の文の意図は、推測であると印を付けて記録する。見出しや表の意図には、その印を指定できなかった。ブロックの意図は、印なしで記録した |
| 意図と文機能を考える手間は、測っていない | 65 文と 27 のブロックの意図を書く量は、本文とは別に要る。かかった時間とトークンは、測っていない |

## 手元の設定との差

| 差 | 根拠 |
| --- | --- |
| 手元の文章の決まりは、守られたかが外から見えない | 手元の `~/.claude` の rules は、「文を主題に結び付ける」「書く前に、文書の仕事と読み手を決める」と定める。決まりとして書いてあるだけで、文ごとの意図は残らない。tsuzuri は、意図を記録として残す |
| 手元は、agent が書いた Issue を、人が読み切れていなかった | 同じ日に、agent が出した 4 つの問いに、thkt が 4 つとも先頭の選択肢を選び、後から別の session に見直しを頼んだ。合意する側が読める量を、超えていた |
| 言い回しを直すスキルは、既に入っている | tsuzuri が仕上げに使う yomiyasu は、手元に導入済みである。同じ日に 3.2.0 から 3.3.0 に上げた |

## 限界

- **効果の測定が無い。** 読み直しが楽になるか、文章が良くなるかを測った数字は、README に無い。手元の試しも、1 つの文書で 1 回である。
- **書かせる流れは、試していない。** 要件定義書と設計書を決め、一文ずつ書かせる流れは、動かしていない。
- **スキルとして導入していない。** 「tsuzuri で読んで」と頼む形ではなく、スキルの手順を読んで、同じ呼び方をスクリプトから行った。
- **引かれた文献を、確かめていない。**
- **公開された当日の版である。** 利用者からの報告は、読んだ範囲に無い。

## 照合の結果

- **照合した主張：** 「文を書く前に意図を書かせる」「文機能を 5 つ付ける」は、スキルの本文と合っていた。「核だけを読めば本筋を追える」は、手元の 1 つの文書では成り立った。
- **読んでいないもの：** `skills/tsuzuri/references/` の各ファイル、テスト、スクリプトと閲覧アプリの中身、README が引く文献。
- **範囲外：** 小説向けの文機能、共有ファイル（`.tsz`）、テンプレートと校正辞書。

## 照合の手順

1. repo の概要と README を読む：`scout repo-overview https://github.com/MaryCache/tsuzuri`
2. スキルの本文を読む：`scout repo-read MaryCache/tsuzuri skills/tsuzuri/SKILL.md`
3. clone して、スクリプトが外へ通信しないことと、書き込む先を確かめる：`grep -n -E 'urllib|socket|subprocess|rmtree|unlink|\.config' skills/tsuzuri/scripts/tsuzuri.py app/server.py`。`subprocess` は `git rev-parse` だけだった。
4. 設定の置き場を一時ディレクトリに向ける：`export XDG_CONFIG_HOME=<一時ディレクトリ>`
5. 記録を作る：`python3 skills/tsuzuri/scripts/tsuzuri.py init <文書>`、続けて `req <記録> --file <推定した要件>`
6. 文ごとに記録する：`memo <記録> --inferred --text <推測した意図>`、続けて `write <記録> --human --text <文> --tags <文機能の JSON>`
7. 見出しと表を記録する：`memo <記録> --block --text <意図>`、続けて `write <記録> --sid <ID> --ver v001 --block <種類の JSON> --text <中身> --tags <対応する要件の JSON>`
8. 検査する：`check <記録>`
9. 閲覧アプリを起動する：`python3 app/server.py <記録> --port 8770`。`127.0.0.1` だけで待ち受ける。

## 見直す条件

- 核の印を、本文を書いていない agent に付けさせて、合意を求められる Issue で試したとき。核だけで合意を決められたか、全文を読んで判断が変わったかを `knowledge/` に書く。
- 表に重要度を付けられるようになったとき、または、表の多い文書を扱う別の方法が分かったとき。
- tsuzuri の効果を測った結果が、公開されたとき。
