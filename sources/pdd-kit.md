# GitHub Next「PDD Kit」の考え方と根拠（2026-11）

PDD Kit は、agent が書いたコードを人が1行ずつ読まずにマージするため、意図を人と揃えたうえで、コードがその仕様を満たすことを形式手法で証明する研究プロトタイプである。その考え方を紹介ページで照合した。自分たちが採用した判断ではなく、手元では動かしていない。

## TL;DR

- PDD Kit は、人がレビューする対象を、コードから意図と仕様に移す。コードが仕様を満たすことは、形式手法で証明する。
- 証明が届かないものがある。検証器が見られないコード、外の世界の事実、人が判断することなどである。
- 対象は Rust だけの研究プロトタイプである。
- 手元では動かしていない。公開日と、コードが公開されているかは確かめていない。

## 中心の主張

**人がレビューする対象を、コードから意図と仕様に移す。** ページは最後の節で「チームは自分たちが何を意図したかを平文でレビューし、証明がコードをそこに縛る」と書く。1行ずつの確認と正しさの保証は、形式手法の証明に任せる。証明できない部分は、テストで補う。

ページが挙げる、agent のコードをレビューするときの問題は4つである。

| 問題 | ページの説明 |
| --- | --- |
| 計画が拘束力を持たない | agent は計画に従う義務がなく、違う扱いをしても何も知らせない |
| テストは作られたものを確かめる | agent がテストも書くため、テストは意図したコードではなく、書かれたコードに合わせて通る |
| 1行ずつのレビューは規模に耐えない | agent が一度に数万〜数十万行を出すと、レビューは流し読みと承認になる |
| vibe verification | モデルに仕様を書かせたり、証明を出すよう調整したりすると、検証は通るが、ほとんど何も制約しない弱い不変条件に落ち着く。「間違った仕様に付いた緑のチェックは、チェックが無いより悪い」 |

## 考え方と根拠

| 考え方 | 仕組み | 照合の結果 |
| --- | --- | --- |
| 判断が要る点ごとに人に問う | 「decision card」で問う。関係するコードの説明を先に示し、答えを「intent artifact」（意図と形式仕様をつなぐ文書）に記録する | ページに例がある。「正しいパスワードの時だけ token を出す」は全員を拒否する実装でも満たせるため、「正しいパスワードなら必ず token を出す」も要るかを問うカード |
| 信頼する境界を明示する | 証明できない部分（bcrypt、DB の参照、時計、JWT の署名）を小さな関数で包み、前提とする契約を付ける。前提を1つずつ人に承認させ、前提の条項ごとにテストを計画に書く | ページに例がある。login では6件の承認が要った。テストは Given/When/Then で書き、実行するまで planned と印を付け、実行後に結果と commit を記録する |
| 仕様は人が読み、証明は機械が確かめる | 仕様の各条項に平文のコメントを付ける。証明は agent が書き、Verus が全ステップを検査する | ページに記述がある。「Verus が証明を受け入れれば、誰が読むかにかかわらず成り立つ」と書く |
| 証明の工程で、契約を弱めない | agent がコードと証明を書き、Verus が検査する。LLM の検証役が「証明も通過したテストも無い要求」を探し、agent に差し戻す。仕様自体の矛盾は、人への判断として戻す | ページに記述がある。async の構文が固定した版の Verus で書けないときは、契約を弱めたり非 async の helper に切り替えたりせず、止まって聞くと書く |
| 仕様にも mutation をかける | `ensures` の条項ごとにバグを1つ仕込み、その条項で Verus が拒否するかを確かめる。生き残った mutant は、その条項が何も制約していないことを示す | ページに記述がある。vibe verification への対策として挙げる |
| PR を領収書にする | PR は、要求ごとに「形式的に証明した」か「テストで確かめた」かを示し、信頼した部分とそれを覆うテストを並べる。人は承認済みの意図と照らして読み、マージする | ページに記述がある |
| 証明で足りたテストを削る | CI に Verus の検査を加える。証明が覆う例示のテストは削り、信頼した部分を守るテストは残す | ページに記述がある。効果は測っていない |
| 被害の大きい所から始める | login、決済、権限から始め、残りを1つずつ検証する | ページに記述がある。例の Pet Store は約5,000行で、検証したのは login だけである |

## 限界

ページ自身が書く限界は、次のとおり。

- **証明が届かないもの。** 検証器が見られないコード（他の crate）、外の世界の事実（DB の中身、時計）、終わるかと速さ、人が判断すること、誰も書かなかった要求。
- **保証の強さは、信頼した部分で決まる。** login では6件で、`check_password` がパスワードについてのすべての約束を、2つの DB の参照が「token がどの account を指すか」の約束を支える。テストが支えるが、証明はしない。
- **対象は Rust だけ。** Verus が Rust の検証器のため。他の言語は Rust に移植するか、検証した Rust を bindings で呼ぶ。
- **証明を作る手間はまだ大きい。** 明確な仕様が手間を抑えると書く。
- **研究プロトタイプである。** 人の時間の使い方を描いた図の幅は、「測定値ではない」と注記がある。

## 手元の資料との関係（未採用）

この節は、照合者が手元の資料と突き合わせて組み立てた案である。どの設定にも入れていない。

| PDD Kit の考え方 | 手元の資料 |
| --- | --- |
| 仕様の条項ごとに mutation をかける | [hadome.md](hadome.md) の `hadome mutate` は、テストの抜けを探す。PDD Kit は仕様の抜けを探しており、対象が一段上にある。テストにも仕様にも「わざと壊して拾うかを見る」という同じ手法を使う |
| 信頼した部品ごとに承認とテストを付ける | hadome の `gate:allow ... reason:` と、[dmmulroy/anti-slop](https://github.com/dmmulroy/anti-slop) の `require-safety-comment-for-type-assertion` は、例外に理由を書かせる。PDD Kit は理由に加えて、例外ごとにテストを要求する |
| 契約を弱めず、止まって聞く | [hill-climb.md](hill-climb.md) のロック対象の拒否と、hadome の終了コード `3` |
| 実装から仕様を引き出し、反例を人に問う | [formal-methods-playbook-mizchi.md](formal-methods-playbook-mizchi.md) は、実装から仕様を吸い出し、Z3 や TLA+ の反例をドメインの人に問う。PDD Kit は向きが逆で、意図から仕様を作り、証明までつなぐ |

Verus を使わずに取り込める考え方は、次の2つである。

1. 仕様やテストの条項ごとにバグを仕込み、何も制約しない条項を見つける。
2. 前提として信頼する部品を名指しし、部品ごとに人の承認とテストを付ける。
