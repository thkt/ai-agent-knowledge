# Claude Code チームが、agent の書いたコードをどう検証しているかを書いた記事（2026-11）

Addy Osmani の記事は、Claude Code チームが検証に使うテストの種類と、検査そのものの運用を書く。記事の全文と、記事がリンクする7ページを読み、手元の設定と feedback-loop に照らした。自分たちが採用した判断ではない。

## TL;DR

- 記事の言う検証は、変更を実際に動かすことである。テストの種類を1つ選ぶなら E2E だと書く。
- 検査は、判定される変更から書き換えられない場所に置く。レビューの規則は base のブランチから読み、合格は commit に結び付ける。
- 新しい gate は、記録だけの段から始める。止めたはずのものを記録し、誤検出を見てから止める段に上げる。
- 検査は、過去の事故と revert で採点する。見逃しは規則に変え、規則は定期的に減らす。
- 数字（約90%、最大10ポイント、39項目）は社内のもので、測り方は記事にもリンク先にも無い。eval の作りの一部は、リンク先の記事の本文で確かめられなかった。

## 中心の主張

**検証の仕組みが、agent に任せられる量を決める。** 記事は、仕組みが無いと人がすべてを確かめるので、同時に動かせる Claude は1つか2つだと書く。仕組みがあれば、数十から数百を並列で動かせると書く。人の仕事は、すべての差分を読むことから、完了の定義を決めて証拠を見ることへ移る、と結ぶ。

### code review の記事

[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)（Addy Osmani、Morgan Westlee Lunt、Qing Wang、2026-10-15）は、同じチームのレビューの流れを書く。

| 項目 | 記事の内容 |
| --- | --- |
| 結果の数字 | 6月から9月に、merge した PR は2倍を超え、revert の割合は40%を超えて下がった。測り方は書かれていない |
| 目標と指標 | ほとんどの PR を、人が1人以下で merge する。人の時間は、PR ごとの承認の数、人のコメントの数、人を待つ時間で測る。revert と事故の割合を、歯止めにする |
| 層 | PR の前の検証、全 PR の AI レビュー、止められるセキュリティのレビュー、止める自動検査、リスクに応じた人の承認、merge queue と段階的な公開、検出と巻き戻しの7つ |
| 指摘の検証 | 複数の agent が同時にバグを探す。別の組が指摘ごとに投票し、十分な数が同意した指摘だけを投稿する。様式、診断、整理だけの指摘は落とす |
| リスクの段 | 低は人の承認が不要、中は1人、高は2人。段は、作者ではなく変更で決まる。分類器が段を選び、2つ目の分類器が、段にかかわらず人が要るかを問う。CI の workflow のファイルは、常に人が見る |
| 承認の範囲 | 承認は、1つの commit に付く。agent の push や手での merge の解決があれば、承認をやり直す。agent の承認は、人の承認に数えない |
| 雑音の測り方 | レビュー役のコメントを、人の反応で分ける。直した、誤りだと言った、意図どおりだと言った、重要でないと決めた、の4つである |
| 雑音の費用 | 作者が agent だと、雑音の費用が上がる。人は細かい指摘を数秒で退けるが、agent は直すので、commit とレビューの回が1つ増える |
| 収束しなかった例 | 1つの PR が、一晩で50回を超えるレビューと修正を重ねた。繰り返し指摘された箇所を `git blame` で調べると、約59%は、最初の回からあったコードだった |
| 収束させる4つの対策 | 3回で打ち切り、作者に方針の見直しを求める。数回目からは、差分だけを見る。バグの型を示し、作者に同じ型をすべて直させる。投稿済みの指摘を繰り返さない |
| `REVIEW.md` の書き方 | 短いものがよい。その repo での失敗の形を述べ、細かい指摘の数に上限を置き、飛ばすパスを挙げ、名前からの推測ではなくファイルと行を証拠に求める |
| まだ無いもの | revert や事故の数が動いたときに、承認を自動で厳しくする仕組みは無い。人の承認なしの merge を増やす前に欲しい、と技術者が言う |

### Code Review のドキュメント

[`REVIEW.md` のドキュメント](https://code.claude.com/docs/en/code-review-customize)と、[PR でのレビューのドキュメント](https://code.claude.com/docs/en/code-review-pull-requests)は、製品の仕様を書く。

| 項目 | ドキュメントの内容 |
| --- | --- |
| 読む版 | `REVIEW.md` は、PR の base か default のブランチから読む。PR の変更からは読まない。レビューの振る舞いを変えるには、先に `REVIEW.md` の変更を merge する |
| 緩める指示の条件 | 重さを下げる指示、パスや問題の種類を外す指示、細かい指摘の上限は、保護された default のブランチから読んだ場合だけ従う |
| 保護の定義 | 更新を制限するか、承認1件以上の PR を求める ruleset を保護と数える。PR を求める場合は、新しい push で承認を取り消すことも要る |
| 保護を確かめられない場合 | `REVIEW.md` を読まない |
| 重さ | Important は merge の前に直すバグ、Nit は止めない小さな問題、Pre-existing は PR が持ち込んでいないバグである |
| 検査の結論 | check run は neutral か skipped で終わる。failure では終わらないので、必須の検査を落とさない |
| 後の回 | push の後に始まる回は、前の回からの変更を見る。細かい指摘と Pre-existing を減らす。変えていないコードへの指摘は、数だけを本文に書き、投稿しない |

## 限界

- **数字の測り方が、記事には無い。** 約90%、最大10ポイント、39項目、3から10項目は、どれも社内の値である。最大10ポイントだけは、別の記事へのリンクを持つ。リンク先にも測り方は無い。
- **著者は当事者である。** 記事は、チームの一員の立場で運用を紹介する。うまくいかなかった運用は書かれていない。
- **E2E の遅さと不安定さへの対処は書かれていない。** 記事は、不安定なテストと遅いテストを害として挙げる。同じ記事は、unit test のほうが速く安定すると書く。E2E を速く安定に保つ方法は、`verify` の skill を Claude に改善させる、という記述だけである。
- **比較の結果が無い主張がある。** レビュー役を1人にすること、回を引き継ぐことは、「より安く、多く見つかる」と書くだけである。
- **止める段は、厳密には止めない。** 理由を書けば通り、2回止めた後は通る。記事は、これを意図した作りとして書く。
- **事故の記録が前提である。** 39項目の一覧と eval は、過去の事故と revert から作る。記録の無い repo での始め方は書かれていない。

### feedback-loop との関係

feedback-loop は、導入先の repo に静的検査と関連テストの反復コマンドを入れる。Non-goals は、自律修正の実行基盤と常駐監視を外している。このため、レビュー役の調整と eval の部分は対象の外である。

| 記事の考え方 | feedback-loop の今 | 参考になる形 |
| --- | --- | --- |
| 見逃しを規則にする条件は、2件以上の PR と、差分から判別できること。出どころは、人のレビューのコメントと PR の revert | #189 は、回数の閾値と、訂正の出どころを決めていない。根拠は、[magpie-agent-development.md](magpie-agent-development.md) の3回である | 閾値の2つ目の例になる。出どころは、どちらも CI から読める。「差分から判別できる」は、lint の規則にできるかの判定に使える |
| 規則の候補を、3つの agent が反証にかける | #189 は、違反の例で落ちることの確認と、既存のコードで当たる件数を求める | 反証の段は #189 に無い |
