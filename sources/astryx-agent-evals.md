# Astryx が agent 向けに作った入口と、agent で設計を決める測り方（2026-11）

Astryx は、Meta が公開したデザインシステムである。README は、人と agent が同じ道具で作ることを設計の中心に置く。UI の部品ではなく、agent 向けの入口の作りと、agent を使って設計を決める測り方を、repo の文書と wiki で照合した。自分たちが採用した判断ではなく、手元では動かしていない。

## TL;DR

- agent の入口は CLI である。agent はパッケージのファイルを読まず、コマンドで文書を引く。CLI の出力の長さを設計の対象にする。
- 設計の選択肢は、白紙の agent に同じ課題を渡して比べる。課題は解き方を名指ししない。変えるのは1つだけにする。
- 採点は、スクリプトで確かめられる部分を決定論的に行い、曖昧な部分だけを別の判定役に任せる。生成した agent に自己採点させない。
- 採点器は、使う前に試す。落ちるはずの入力が落ち、通るはずの入力が通らなければ、実行を止める。
- Astryx とほかのライブラリを比べた結果の数字は、読んだ範囲に無い。読めた結果は、prop の名前を決めた実験1件である。

## 中心の主張

**規約は主張せず、測って決める。** README は、原則の1つを「Earned by measurement」と呼ぶ。規約を試し、結果を緩く持ち、新しい状況が誤りを示したら見直すと書く。もう1つの原則は、人と AI に1つの仕組みを使わせることである。AI に使いやすくした変更は、どれも人にも使いやすくなったと書く。この主張に、件数は付いていない。

## 測り方

repo には、測り方が2つある。wiki の手引きに沿う比較と、ブラウザで採点する eval である。

| 考え方 | 原文の記述 | 照合の結果 |
| --- | --- | --- |
| 走らせる前に、4つを決める | 何が勝ちを決めるか。素朴な課題はどういう形か。何を比べるか。誰が走らせ、誰が採点するか。agent は、各項目に既定の案を出し、利用者に反応させる | wiki に記述がある。評価の軸と、同点のときの決め方を、走らせる前に決めるとする |
| 課題は、解き方を名指ししない | 課題は、利用者の体験を述べる。部品やライブラリの名前を入れない。5件から15件を用意し、易しいもの、差が出るもの、端の場合、どの条件でもできないことを含める | wiki と eval の README に記述がある |
| 変えるのは1つだけにする | 課題、人物の設定、出力の形式を、すべての条件で同じにする。片方にだけ意味のある助言を入れない。両方を使える条件を足すと、agent が自然に選ぶほうが分かる | wiki と `vibe-tests/README.md` の Checker Protocol に記述がある |
| 答えを漏らさない | 期待する部品の一覧は、採点にだけ使う。課題にも、検索のコマンドにも入れない | Checker Protocol に記述がある |
| agent は白紙で起動する | 課題と条件の組ごとに、新しい agent を1つ起動する。親の会話も、メモリも引き継がない。1つの agent に複数の条件を続けて処理させない | wiki に記述がある |
| 汚染の兆候を知っておく | すべての条件で幻覚が0件。すべての条件の点数がほぼ同じ。迷いの無い高い確信。1つの agent が複数の条件を処理した | wiki に記述がある。根拠の件数は示されない |
| 生成した agent に、自己採点させない | 生成する agent は、成果物と、頼ったもの、迷った点、回避策を報告する。点は付けない。別の判定役が、全条件の成果物を並べて採点する。スクリプトで確かめられる部分は、判定役に回さない | wiki に記述がある |
| 一度きりの判断は、表で済ませる | 多くの比較は、いま問いを決めるためのもので、結果の表が成果物である。保存の形式と報告の仕組みは、経過を追うときだけ作る | wiki に記述がある |
| 1件の失敗に合わせて直さない | agent が当たった1件をそのまま直すと、その1件に合わせすぎる。複数の実行で繰り返す型を求め、直す前に再現する | wiki に記述がある |
| 採点は、ブラウザで見える振る舞いで行う | eval は、LLM の判定を使わない。型検査、ビルド、ブラウザでの操作、未捕捉の例外の4つがすべて通ると合格である。スクリーンショットとアクセシビリティの件数は証拠として残し、合否を変えない | eval の README に記述がある |
| 採点器を、使う前に試す | 採点の前に、モジュールの欠落と未知の prop を持つファイルが、型検査とビルドで落ちることを確かめる。空の雛形が通ることも確かめる。どちらかが違えば、実行を止める。`--self-test` は、模範解答がすべて通り、空の雛形がすべて落ちることを、モデルを呼ばずに確かめる | eval の README に記述がある |
| ハーネスの影響を消す | agent は `claude -p --bare` で起動する。利用者の設定、plugin、hook、MCP、メモリを読まない。Web の道具と subagent は切る。モデルは完全な ID で固定し、別のモデルで始まった実行は止める | eval の README に記述がある。手元の Claude Code 2.1.325 にも `--bare` がある |
| 実行の後で、不正を監査する | 記録を読み、repo、ホーム、ほかの実行の中を読んだ実行を失格にする。agent が起動に失敗した実行は、ライブラリについて何も言わないので、合格率から外す | eval の README に記述がある。監査はサンドボックスではなく、すり抜ける書き方を「既知の穴」に挙げる |
| 差に区間を付ける | 課題ごとに、条件あたり3回走らせる。合格率に95%の Wilson の区間を、条件の差に Newcombe の区間を付ける。差の区間が0を含めば、雑音である | eval の README に記述がある。同じ課題の実行は独立でないので、課題が少ないと、実際の不確かさは表示より広いと書く |
| 費用に上限を置く | 総額の上限と、1回あたりの上限を持つ。上限に収まらない実行は、始めない | eval の README に記述がある |
| 不公平は、相手に有利な向きで残す | 採点の非対称を3つ挙げ、どれも比較相手に少し有利だと書く。Astryx が勝ったときの信頼が上がる、という理由である | `vibe-tests/README.md` に記述がある。古い夜間の pipeline の話で、静的な採点である |

## 読めた結果：prop の名前を決めた実験

`Stepper` に足す prop の名前を、4案で比べた記録である。案は、真偽値2つの名前が3通りと、列挙型1つである。4つの課題と4案の組ごとに agent を起動し、名前を伏せて書かせる agent 5つと、判定役1つを足した。計22である。

- **案の文書は、1つのテンプレートから機械で作った。** 導入、prop の表、例は1バイトも違わず、名前だけが違う。語数は349、349、349、354である。
- **使えるかどうかでは、差が出なかった。** 16件すべてが正解で、幻覚は0件だった。記録は、wiki の判断の型に従い、すべての案が同じコードを生むなら差は重要でないと書く。
- **差が出たのは、名前を伏せて書かせた5件である。** 5件すべてが真偽値2つを書き、列挙型は0件だった。4件が、既存の `label` prop と衝突する名前を退けた。
- **判定役は、点数に出ない差を拾った。** 2案では、該当の8件のうち4件すべてで、agent が「この prop はデスクトップの表示を消さないか」を確かめに行った。残りの2案では、0件だった。
- **目隠しはできなかった。** 案が prop の名前から分かるためである。判定役には、好みではなく基準で採点し、結果を読む前に文書の同等性を確かめるよう指示したと書く。

この実験では、16件すべてが正解で幻覚も0件という、wiki が汚染の兆候に挙げる形が出ている。記録は、これを汚染としては扱っていない。

## 限界

- **比較の結果は、読んだ範囲に無い。** eval は Astryx と shadcn/ui を比べる設計だが、合格率は repo の文書に載っていない。README の「13,000超のアプリ」「8年」も、再現できない自己申告である。
- **試行の5課題は、差を出さない。** eval の README は、`pilot` の5課題を、どちらの条件でも白紙の agent がすべて通すと書く。比較に使うのは `v1` の課題である。
- **eval は、ハーネス1つ、ブラウザ1つである。** Claude Code と Chromium だけで、結果はそのハーネスとモデルについてのものだと書く。
- **回数が少ない。** 既定は条件あたり3回で、名前の実験は案あたり4件である。
- **監査は、サンドボックスの代わりにならない。** 読んだ場所を変数や符号化で隠した実行は、警告にしかならない。README は、隔離したファイルシステムで走らせれば塞がると書く。
- **作者は当事者である。** 比較の対象は自分たちのライブラリである。

## 照合の手順

1. 版を確かめる：`gh api 'repos/meta/astryx/commits?per_page=1' --jq '.[0].sha'`
2. ファイルの一覧から、agent に関わるものを探す：`scout repo-tree meta/astryx` の出力を、`AGENTS.md`、`SKILL.md`、`vibe-tests` で絞る。
3. 文書を読む：`scout repo-read meta/astryx <path>`。path は、項目の表のとおりである。
4. wiki を取得する：`scout fetch https://github.com/meta/astryx/wiki/Designing-Vibe-Tests`
5. 手元の CLI の flag を確かめる：`claude --help | ugrep -i bare`
