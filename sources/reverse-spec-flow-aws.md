# AWS Japan「Reverse Spec Flow」：既存のコードから仕様書を起こす手順と、抜き取りで誤りの割合を測る方法（2026-11）

AWS Japan は、仕様書の無いアプリケーションのソースから、agent 向けの仕様書を作る手順（Reverse Spec Flow）を公開した。紹介の記事を読み、手元の頁の書き方（記述ごとの根拠、確かめたものと確かめていないものの区別）と突き合わせた。道具は、手元で動かしていない。採らない、と判断した。手がかりになった点を 1 つ残す。

## TL;DR

- 道具は、採らない。解いている問題は、仕様書が無く、大きく、書いた人に聞けないコードの引き継ぎである。手元の repo は、どれも当たらない。
- 手順の芯は 4 つである。記述ごとに根拠の位置を付ける。書いた AI と別の AI が、引用した行が記述を裏付けているかを確かめる。確かめられないことは「不明」と書く。完了は、数えて決める。
- 手がかりになったのは、点検の後の抜き取りである。記事は、点検を通した仕様書から記述を無作為に 200 件抜き、原典と照らした。約 5% に一部の誤りがあり、完全に誤った記述は 0 件だった。
- 手元の頁は、根拠と「確かめていないこと」を書いているが、誤りの割合を測ったことは無い。
- 抜き取りは、手元でまだ試していない。照合日は 2026-11-24。

## 中心の主張

**AI の賢さに頼らず、誤りが入りにくく、入っても見つけやすい手続きに AI を従わせる。** 記事は、仕様書の質が、それを入力にした作り直しの質を決める、と述べる。仕様書に無い業務の決まりは新しいシステムから消え、仕様書の誤りはそのまま作り込まれる、と書く。

## 考え方と根拠

| 考え方 | 記事の記述 | 照合の結果 |
| --- | --- | --- |
| 「仕様書を書いて」と頼むだけでは、足りない | 根拠の無い記述が混ざる。主な部分だけで「完成」と報告する。今の技術の都合が、仕様として書かれる。画面、帳票、バッチの順のように、コードから読みにくい部分が抜ける | 記事の記述だけである。試す中で繰り返し見た、と書く |
| 確かめた記述と、確かめていない記述が、同じ見た目で並ぶ | AI が書いた仕様書を受け取った AI は、2 つを区別できず、同じ確かさだと判断する | 記事の記述だけである |
| 段を 5 つに分ける | 対象の commit を固定する。部品とつながりの一覧を作る。観点ごとに、根拠つきで分析する。仕様書を書く。書いた段とは独立して、網羅、引用、事実と推測の区別を点検する。段の境界では、人に確認を求める | 記事の記述だけである |
| 記述ごとに、根拠の位置を付ける | 仕様書の各記述に、コードの位置（ファイルと行）を付ける。根拠の無い断定は、残さない | 記事の記述だけである |
| 確かめるのは、書いた AI と別の AI である | 書いた AI が見直すと、同じ思い込みで見落とす。検証役は、位置があるかだけでなく、引用した行が記述を本当に裏付けているかを確かめる | 記事の記述だけである。repo には、検証役を書き手から切り離すための hook と script がある |
| 確かめられないことは、推測で埋めない | 「不明」として残す。既にある設計書は、出所の分かる、まだ確かめていない主張として扱う。コードと矛盾した記述は、ずれとして記録する | 記事の記述だけである |
| 完了は、数えて決める | 最初に作る一覧を、網羅の分母にする。全部の要素が仕様になるまで、完了しない。完了は、AI の報告ではなく、点検の script が成功を返すかで決める | 記事の記述だけである |
| 今の技術に依存する層と、本質の層を分ける | 分ける基準は、作り直す先がどの技術でも、この内容は要るか、である | 記事の記述だけである |
| 点検の後に、抜き取りで誤りの割合を測る | Apache Roller（約 15 万ステップ）の仕様書から、記述を無作為に 200 件抜き、原典と照らした。約 5% に一部の誤り（一覧の不足、条件の欠落、言い過ぎ、引用の位置のずれ）があった。完全に誤った記述は 0 件だった | 記事の記述だけである。抜き取りを誰が行ったか、誤りの判定の基準は、書かれていない |
| 誤りは、0 にはならない | 保証はしない、と書く。仕様書をもとに作り直したものは、受け入れのテストで、今のシステムと同じに動くことを確かめる | 記事の記述だけである |

## 採らない理由

道具に固有の部分は、大きく古いコードの引き継ぎのためにある。技術ごとの数え方の手引き、網羅の分母を作る段、技術に依存する層と本質の層の区別、ID と索引である。

手元の repo は、自分で書いた小さい TypeScript の repo で、判断記録と契約の文書があり、書いた本人がいる。記事の例は、15 万ステップに約 38 時間かかっている。作り直し向けの設定は、保守向けの 5〜7 倍の費用がかかる、と記事が書く。得るものより、重さが上回る。

仕様書の無い他者のコードを引き継ぐ場面では、当たりうる。その場合、生成した仕様書にはコードの抜粋が入るので、ソースと同じ扱いが要る、と記事が書く。

## 手がかりになった点

手順の 4 つの芯のうち 3 つは、手元で既に行っている。

| 手順の芯 | 手元 |
| --- | --- |
| 記述ごとに、根拠の位置を付ける | この repo の `sources/` の頁は、考え方ごとに「照合の結果」の列を持つ。thkt/dotclaude#959 は、Issue ごとに根拠の行を求める |
| 位置があるかではなく、裏付けているかを確かめる | #959 は、行があるだけでは足りる理由にせず、所在を開いて確かめる、と定める |
| 確かめられないことは、「不明」と書く | `sources/` の頁は「確かめていないもの」を持つ。`notes/` の頁は、資料の記述、手元の資料、筆者の推測を分ける |
| 点検の後に、抜き取りで誤りの割合を測る | **行っていない** |

欠けているのは、4 つ目である。手元の頁は、根拠を付け、確かめていないことを書いている。しかし、書いた後に無作為に抜いて原典と照らし、どれだけ誤っているかを数えたことは無い。

この欠けは、同じ 2 日間に 2 回出ている。

- `sources/` の頁の多くは、agent の要約を通して読んだ資料から書いた。頁には「要約で確かめた」「原文で確かめた」と書き分けたが、要約がどれだけ正しいかは、測っていない。
- 人のレビューを残す場所を整理したとき、`sources/` の頁は読まずに merge してよい側に入った。その頁に、どれだけ誤りが残るかは、分からないままだった。

抜き取りは、道具を入れずに試せる。開いている頁から記述を数十件抜き、出典と照らし、一部の誤りと完全な誤りを分けて数える。記事の 200 件と 5% は、比べる目安になる。

## 限界

- **著者は、道具の提供元である。** 別の人による追試は、示されていない。
- **抜き取りの手順が、書かれていない。** 誰が照らしたか、何を誤りと数えたかが分からないので、5% を手元の値と直接は比べられない。
- **道具は、静的に読むだけである。** 動かして確かめることはしない、と記事が書く。
- **repo の中身を、読んでいない。** 点検の script が何を確かめるかは、記事の説明に頼っている。

## 照合の手順

1. 記事を取得する：`scout fetch <出典の URL>`。
2. repo のファイルの一覧を見る：`scout repo-tree aws-samples/sample-reverse-spec-flow`。
3. 手元の頁の作りを、記事の 4 つの芯と 1 つずつ照らす。

## 見直す条件

- 手元の頁で、抜き取りの照合を行ったとき。誤りの割合と、誤りの種類を `knowledge/` に書く。
- 仕様書の無いコードを引き継ぐ作業が出たとき。道具を採るかを、repo の中身を読んでから決め直す。
- 記事の抜き取りの手順が公開されたとき。
