# 弁護士ドットコム「フロントエンドのテストカバレッジは 100% 強制がいい」の考え方と根拠（2026-11）

弁護士ドットコムの辻 佳佑は JSConf JP 2026 で、フロントエンドのカバレッジの閾値を 100% にして CI で強制した経験を発表した。スライドの全部を読み、手元の検査（テストの強さを確かめる mutation と、何も確かめないテストの決まり）と突き合わせた。手元で、カバレッジの閾値は試していない。自分たちが採用した判断ではない。

## TL;DR

- 主張は、閾値を 100% にして、外す箇所には理由つきのコメントを書かせる形がよい、である。80% の閾値では、残りの 20% がどこで、なぜテストしないのかが残らない。
- 100% への 2 つの懸念（費用が割に合わない、価値の低いテストが増える）は、人がテストを書く前提だった、と発表は述べる。AI で書く手間は消えたが、怪しい除外のコメントと、何も検証しないテストが生まれた。
- 手当ては 2 つである。除外のコメントは、型を直す、関数を切り出す、テストを書く、のどれかで消す。何も検証しないテストは、lint と AI で見つけて直す。
- 測った数字は無い。カバレッジの前後、除外のコメントの件数、かかった時間は、載っていない。
- 発表者は、カバレッジで分かるのは実行されたかまでだ、と注に書く。照合日は 2026-11-23。

## 中心の主張

**全部を対象にし、外す箇所は場所と理由を残す。** 発表は、開発中のプロダクトで Vitest のカバレッジの閾値を 100% にし、CI で強制した、と述べる。

## 考え方と根拠

| 考え方 | 発表の記述 | 照合の結果 |
| --- | --- | --- |
| 100% への懸念は、2 つである | 100% に近づけるほど、費用が割に合わない。価値の低いテストが増えて、負債になる | 発表は、Google Testing Blog の記事（2020）と、Kent C. Dodds の記事（2019）を出典に挙げる。出典の先は読んでいない |
| 懸念は、人がテストを書く前提だった | AI で修正の費用が下がった今は、問題を 1 つずつ、指標を持って直させれば済む、と述べる | 発表の記述だけである |
| 100% にすると、別の問題が出た | 書く手間は、AI でほぼ消えた。代わりに、怪しい `v8 ignore`（集計から外すコメント）が大量に入った。カバレッジを埋めるだけで、何も検証しないテストが生まれた | 発表の記述だけである。件数は示されない |
| 閾値 100% と除外のコメントは、場所と理由を残す | 閾値が 80% だと、残りの 20% の場所も、テストしない理由も分からない。100% と除外のコメントなら、コメントの位置と文面で分かる | 発表の記述だけである |
| 除外のコメントは、4 つの型に分かれる | 型を実態に合わせれば要らなくなるもの。関数に切り出せばテストできるもの。本当はテストできるもの。正しい除外で、残すもの | 発表の記述だけである。4 つの型の割合は示されない |
| 型が実態より広いなら、狭める | 例は、表示されるときには必ずある値の型に、無い場合が入っているものである。AI は、届かない分岐を書いて、除外のコメントを付ける。型から外すと、分岐もコメントも要らなくなる | 発表の記述だけである |
| 型が実態より狭いなら、広げる | 例は、名前が無い場合があるのに、引数の型がそれを許さないものである。呼ぶ側が空の文字に変え、除外のコメントを付けている。型に含めると、変換が要らなくなり、テストも書ける | 発表の記述だけである。発表は、除外を直すと、隠れた不具合の修正につながる、と述べる |
| 届かないと書かれた箇所に、テストを書く | 例は、「エミュレーションでは届かない」と書かれた、外側のクリックで閉じる処理である。クリックのテストを書くと、届いた | 発表の記述だけである |
| 形で分かるテストの問題は、lint で見つける | 実装の値を含まない `expect`。アサーションの無いテスト。条件によって `expect` が走らないテスト。1 つ目は自作の規則、残りは Vitest 向けの既存の規則を使う | 発表の記述だけである |
| 意味の理解が要る問題は、AI で見つける | テストの名前と中身が合わないもの。モックに返させた値を、そのまま確かめるもの | 発表の記述だけである |
| 手当ては、定期的に AI に行わせる | AI がテストを書くたびに、問題は生まれ続ける。AI が定期的に確かめ、直す PR を出す | 発表の記述だけである。頻度と、PR の数は示されない |
| 100% にすると、変更の影響に気づきやすい | 依存の更新の PR を、ためずに merge しやすい。整理の変更を、続けやすい | 発表の記述だけである。気づいた回数は示されない |
| カバレッジで分かるのは、実行されたかまでである | mutation のテスト、見た目の比較、E2E で、検出を強められる、と注に書く | 発表の記述だけである |

## 限界

- **測った数字が無い。** カバレッジの前後、除外のコメントの件数、4 つの型の割合、定期の確認が直した件数は、載っていない。
- **1 つのプロダクトでの経験である。** 規模、テストの数、チームの人数は、書かれていない。
- **除外のコメントを残す基準は、例が 1 つである。** 開発のときだけ動くコードの例だけが示される。
- **実行されたことと、確かめたことは別である。** 発表は、何も検証しないテストを lint と AI で見つける、と述べる。見つけ損ねた割合は、分からない。

## 手元の進め方との関係（未採用）

この節は、照合者が、2026-11-23 の時点の手元の検査に、発表の考え方を当てはめた結果である。発表の主張ではない。

| 発表の考え方 | 手元の検査 | 差 |
| --- | --- | --- |
| 全部を対象にし、外す箇所は理由を残す | feedback-loop が乗り換える先の道具は、テストをすり抜けた壊し方を、理由つきで記録のファイルに残す（thkt/feedback-loop#253） | 対象が違う。発表は、行が実行されたかを見る。手元は、コードを壊したときにテストが落ちるかを見る |
| 除外を直すと、型と設計が直る | 手元で、すり抜けた壊し方の記録を、型の直しに使ったことは無い | 発表の 4 つの型は、すり抜けた壊し方を読むときの分け方として使える |
| 何も検証しないテストを、形で見つける | dotclaude の決まりは、何も確かめないテストの形を 5 つ挙げる | 手元は、決まりの文である。lint の規則にはしていない |
| 手当てを、定期的に行わせる | 手元の定期の実行は、Bug の出どころの集計だけである | テストの質を定期に見る実行は、無い |
| カバレッジの閾値を、CI で強制する | 手元の repo が、カバレッジを測っているかは、確かめていない | 手元の検査は、関係するテストの実行と、壊し方での確認に置いている |

## 照合の結果

- **照合した主張：** 発表の主張は、発表の中の記述だけで成り立っている。外の資料と突き合わせた行は無い。
- **読んでいないもの：** 発表が出典に挙げる 2 つの記事。発表の音声と、質疑。
- **確かめていないもの：** 発表が挙げる lint の規則の、今の名前と動き。

## 照合の手順

1. 資料を取得する：`scout fetch https://speakerdeck.com/bengo4com/20261122-jsconfjp2026-coverage-100`。文字起こしが返る。図とコードが中心のスライドは、文字起こしに入らない。
2. 文字起こしに無いスライドの画像を取得する。画像の URL は、`slide_<番号>.jpg` の形で、番号は 0 から始まる。
3. 画像を agent に読ませる。agent には、既に読んだスライドの番号と、外の知識を足さないことを伝える。

## 見直す条件

- 手元の repo で、カバレッジを測ったとき。壊し方での確認と、どちらが先に穴を見つけるかを比べる。
- 何も確かめないテストの形を、lint の規則にしたとき。発表の 3 つの規則と、手元の 5 つの形を突き合わせる。
- 発表者が、件数か、定期の確認の結果を公開したとき。
