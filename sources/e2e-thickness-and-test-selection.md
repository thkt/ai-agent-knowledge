## 中心の主張

AI と E2E の関係を論じているのは kuniwak とポリコの2件で、両者は次の点で一致する。**E2E は毎回すべてを回さず、入力や分岐の組み合わせは下の層のテストに置く。**

理由の述べ方は異なる。kuniwak は、AI を使っても E2E の実行時間や組み合わせの数といった数理的な制約は変わらないとする。ポリコは、書く・直す負担が下がったことを理由に E2E を広げた。そのうえで、変更のたびに関係のない機能まで回したくないという理由で、普段は関係するシナリオだけを回す。計算の端数や入力の組み合わせは単体テストに残している。

もう1つ一致するのは、期待値を実装からではなく仕様から取ることである。kuniwak は、実装後に書くテストが実装の挙動を追認しやすいと書く。ポリコは、AI に操作手順ではなく仕様上の結果を伝えると書く。

## 資料の間で食い違う点

1. **E2E の厚さ。** kuniwak はパターンBの例（チェックアウト処理）で、E2E には代表1シナリオだけを足すよう AI に指示する。E2E の構成として推奨するのは、状態遷移モデルによるグラフベーステストと、高価値シナリオを固定した例ベーステストの併用である。次善策は、エラー推測と高価値シナリオの併用とする。ポリコは、対象と観点ごとにシナリオを用意する。
   - 両者とも、入力や分岐の組み合わせは下の層に置く点で一致する。
   - 違いは「代表」の単位である。ポリコの観点の例（通常動作、保存後に値が残る）は、どちらも画面・API・DB を結合しないと確かめられない性質である。この読み方は照合者の解釈で、両記事には書かれていない。
2. **テスト選択。** kuniwak（2026-11-04）は、現実の規模で使えるテスト選択の手法を見たことがないと書く。ポリコ（2026-10-26）は、静的な対応表と AI の判断を組み合わせて選んでいる。ただしポリコの記事に、選択の取りこぼしの件数は書かれていない。
3. **ゲートの置き場所。** GitLab は CI の blocking にゲートを置く。ポリコは、ローカルの開発ワークフローでテストを実行して結果を PR に貼る。そのため、実行漏れを防ぐ役割では CI の価値が相対的に下がったと書く。CI が不要とまでは書いていない。

## 資料から組み立てた方針案（未採用）

この節は、照合者が資料を突き合わせて組み立てた案である。どのプロジェクトでも試していない。`knowledge/` に移す前に、節の最後に挙げる指標を測る。

前提のスタックは、Vitest と Testing Library、Playwright、TypeScript の API と Postgres、CI である。

### E2E に入れるもの

| E2E に入れる | 理由 |
| --- | --- |
| 画面・操作ごとの代表シナリオ1本 | 画面→API→DB のつなぎ目の結合バグは、結合しないと出ない（kuniwak） |
| 保存して開き直しても値が残ること | 永続化は、画面単体でも API 単体でも確かめられない（ポリコ） |
| 不正な入力が保存されないこと | エラー表示だけでなく、DB に書かれていないことまで見る（ポリコ） |
| 権限ごとに、操作できること・拒否されること | ポリコは権限を網羅の対象に含める |

| E2E に入れない | 置き場所 |
| --- | --- |
| 計算や入力値の分岐と、その組み合わせ | Vitest の単体テスト（kuniwak） |
| コンポーネントの表示の分岐、操作への反応 | Testing Library のテスト。要素は role で取り、DOM 構造に依存させない（Desiderata の Structure-insensitive） |
| API のバリデーション、DB の制約 | 本物の Postgres を使う API の結合テスト（SWE本） |
| 外部の認証・送信サービスとの接続 | ローカルではテストダブルに置き換え、本物とは staging の smoke で確かめる（kuniwak、ポリコ） |

### 実行する場面

| 場面 | 回すもの | 失敗したとき |
| --- | --- | --- |
| エージェントがファイルを編集するたび | 型チェック、`vitest --changed` | エージェントは次の編集に進まない |
| エージェントがタスクを完了するとき | 単体・結合テストの全件、関係する E2E | PR を出さない |
| PR の CI | 単体・結合テストの全件、E2E の `@smoke`、関係する E2E | merge を止める |
| main へのマージ後、または夜間 | E2E の全件 | merge は止めない。失敗は issue にする |
| staging と canary へのデプロイ | 本物の外部サービスにつないだ E2E の smoke | デプロイを止める（GitLab） |
| 本番デプロイ後 | smoke | 止めない（GitLab） |
| 大規模なリファクタ | ローカルで E2E の全件 | PR を出さない（ポリコ） |

### 選択の仕組み

1. **段階1：** Playwright のタグ（`@smoke`、機能領域ごとの `@profile` など）と、ソースのパスからタグを引く設定ファイルで、回す E2E を選ぶ。`shared/`・`api/`・`domain/` の変更では、使っている画面を調べて対象のタグを広げる。
2. **段階2：** ポリコの対応表に移る。抽出器だけで1,787行あるため、段階1の取りこぼしを実測してから導入を判断する。

全件実行で落ちたテストがその変更の PR で選ばれていなかったら、タグの設定ファイルを直す。

Playwright の `--only-changed` は、変更されたテストファイルを回す機能である。そのため、アプリのソースを import しない E2E は、アプリ側の変更では選ばれないと照合者は推測する。この挙動は実行して確かめていない。

### エージェント向けルールの案

```
- テストの期待値は issue と仕様から書く。実装を動かした結果を期待値にしない。
- 既存テストの assertion を変えるときは、根拠になる仕様変更を PR に書く。根拠なしで直してよいのはセレクタだけ。
- E2E では操作手順に加えて、仕様上の結果を確かめる。例：保存後に開き直しても値が残る。不正な入力は保存されない。
- 分岐の多いロジックは純粋関数か strategy に切り出す。分岐は単体テストで網羅し、E2E には代表シナリオを1本だけ足す。
- E2E の失敗原因がロジックの分岐だった場合は、その分岐の単体テストを先に追加してから直す。
- 仕様が確定しているタスクでは、実装の前に E2E を書く。
- skip されたテストを成功に数えない。対象の viewport（PC・モバイル）すべてで成功したことを確認する。
- 探索テストで見つけた指摘は、再現してから issue にする。
- sleep や waitForTimeout で待たない。Playwright の自動待機つき assertion を使う。
- CI では Playwright の forbidOnly を true にする。
```

### 採用前に測るもの

| 指標 | 判断すること | 測り方 |
| --- | --- | --- |
| PR の選択から漏れ、全件実行で見つかった失敗の件数 | 段階2の対応表を入れるか | 全件実行で落ちたテストが、その変更の PR で選ばれていたかを照合する |
| flaky の件数 | どのテストを直すか、隔離するか | Playwright の reporter で `outcome()` が `"flaky"` を返したテストを数える |
| E2E の全件の実行時間 | 全件を PR で回すか、マージ後に回すか | CI の実行ログから読む |
| staging と本番で見つかった欠陥と、それを検知すべきだった層 | テストの置き場所を見直すか | 欠陥の issue に、検知すべきだった層を記録する |

- **再計算した数値：** すべて一致した。0.999¹⁰⁰ = 0.9048、4⁴ = 256、4⁴×4 = 1,024、784 / 31,979 = 2.45%、3+7+16 = 26。

- **CLI と型定義：**

## 見直す条件

- E2E の1件あたりの実行時間か不安定さが桁で下がったとき。例えば、e2e.com のリプレイの効果を第三者が測ったとき。kuniwak の実行時間と不安定さの制約が弱まる。
- テスト選択の取りこぼし率を測った事例が公開されたとき。
- GitLab の Testing Strategy が改訂されたとき。公開日が無いため、照合日の版と比べる。
- ポリコが、対応表の取りこぼし件数か、e2e の Test Filters API への移行結果を公開したとき。
